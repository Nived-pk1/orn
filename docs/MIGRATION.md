# Migration

Package section **#27 Migration from v6**, plus schema-version migrations (#10 uses the same machinery for curriculum data). Contracts: `src/core/migrations/contracts.ts`, `src/io/contracts.ts` (`LegacyImportReport`). Fixtures: `data/fixtures/legacy/`.

## 1. Schema versioning

- `CURRENT_SCHEMA_VERSION` (integer) lives in `src/core/schema/dataset.ts`. It is stored in `meta.schemaVersion` and in every export.
- **Bump rule:** any change that a strict older reader would reject bumps the version — new fields, new record kinds, and enum widening included. Pure documentation changes do not.
- Every version keeps a frozen fixture set in `data/fixtures/schema/v<N>/` (at minimum `minimal-valid.orn.json` and a maximal fixture that uses every field). Fixtures of old versions are never edited.
- An app that finds a newer version on disk or in a file opens read-only / refuses the import with an explanation; it never guesses.

## 2. Migration framework

- One pure, deterministic `SchemaMigration` per step (`from → from + 1`) in `src/core/migrations/steps/`. The runner applies steps in order on the **tolerant envelope** (records as unknown), then the result is parsed with the current strict schemas. `run` returns a value, never throws for document problems: `{ ok: true, doc, steps }` or `{ ok: false, code, message, atVersion }` with code `INVALID_VERSION`, `NEWER_VERSION`, `MISSING_STEP`, `STEP_FAILED` or `STEP_CONTRACT`; it verifies each step's output version and report, and returns no partial result.
- Runs in the compute worker. Stored data: `pre_migration` snapshot → migrate → full L1–L3 → `replaceAll` in one transaction. Any failure restores the snapshot and opens read-only (PERSISTENCE.md §12).
- Every step returns a `MigrationStepReport` (changed record IDs, notes) that is stored with the import batch or shown after an on-disk migration.
- Tests per step: the frozen `v<N>` fixtures migrate to documents equal to the committed expected `v<N+1>` outputs; the chain from v1 to current is tested; migrated data round-trips (P-03); undo history is empty after migration (history never spans versions).

## 3. Rules for writing a migration

1. Never drop information. Values without a new home go to `provenance.legacy.unmapped` of the affected record and into the report (INV-23).
2. Never infer chemistry silently. A value that must be interpreted gets `review.status = review_required` with a reason.
3. Deterministic: same input → same output, including generated IDs (derive from existing IDs + a stable hash).
4. Migrations never read the clock except through the injected context, and use the document's `exportedAt` as the timestamp for created records.
5. Migrations are data-only: they cannot depend on UI code or on the current app's non-schema modules.

### 4.2 Deterministic IDs

Legacy IDs are sanitised to `[0-9a-z-]` (lowercase, other characters → `-`); if sanitising changed the value, `-<6-char hash>` of the original is appended. Then:

| Created record | ID |
|---|---|
| species / class from compound `c15` | `spc_v6-c15` / `cls_v6-c15` |
| reaction `r5` | `rxn_v6-r5`; nested `prt_v6-r5-<n>`, `stg_v6-r5-<n>`, `out_v6-r5-1`, `pdt_v6-r5-<n>`, `int_v6-r5-<n>` (step 3.11a: intermediates). For participants, products and intermediates `n` is the 1-based position of the participant in the legacy list, so a participant that is not imported leaves a gap and never renumbers the others; stages are `-1` (reaction) and `-2` (workup) |
| record created from a free-text label | `rgt_v6-l-<slug>-<hash6>` / `spc_v6-l-<slug>-<hash6>` (deduplicated by folded label) |
| concept, named reaction, topic from text | `cpt_v6-<slug>-<hash6>`, `nrx_v6-…`, `top_v6-…` (reuse existing records matched by folded name/alias first) |
| concept of a kind-specific role (step 3.11b review) | `cpt_v6-<slug of the text>-<hash6 of "<conceptKind>\u0000<folded text>">` for `reaction_type`, `mechanism_class`, `reaction_family`: one text under two kinds is TWO concepts. The generic roles (`jee.prerequisites`, `jee.concepts`) keep the folded-text key and reuse any concept of that name (dataset first, then one this import made; several: the first by ID, said on the reaction) |
| trap → caveat | `cav_v6-r16-<n>` |
| relevance | `erl_v6-r16-main`, `erl_v6-r16-advanced` |
| related reactions | `rel_v6-<lower id>-<higher id>` (symmetric, one per pair) |
| mechanism made from `mechanism.summary` (step 3.11b) | `mec_v6-<reaction part>` (one per reaction) |
| topic mapping of a reaction's `chapter` (step 3.11b) | `tmp_v6-<reaction part>` (one per reaction) |
| transformation made from `fgFrom` / `fgTo` (step 3.11b) | `trf_v6-<slug>-<hash6>` of the key `[[sorted fgFrom],[sorted fgTo]]` (`transformationKey`: the functional-group ids, de-duplicated and sorted, as JSON); the first reaction with a class set names the record |
| image | `ast_v6-<first 16 hex of sha256>` |
| hub anchor / display | `anc_v6-c6`, `edp_v6-c14` |
| `functional_group` class made from a functional-group id (step 3.10) | `cls_v6-fg-<part>` (the id itself when already `[0-9a-z-]`, else sanitised + hash) |
| class made from a `compoundClass` text (step 3.10) | `cls_v6-l-<slug>-<hash6>` of the folded text (one per folded text) |

Re-importing the same file therefore produces identical IDs, and the conflict analysis resolves them as `identical_skip`. That holds when the import runs with the same clock: the legacy file carries no time, so the clock supplies `provenance.createdAt` and `provenance.updatedAt`. With a DIFFERENT clock every incoming record differs from the stored one in exactly those two fields, so nothing is recognised as identical and the default resolution is `keep_current` on every record (nothing is lost or duplicated; the user sees a conflict per record). Step 3.11c review decision, NOT built yet (Phase 5, with the import UI): when the same file (same SHA-256 of its bytes) was imported before, the session reuses the clock time recorded for that earlier batch. The identical rule and the conflict analysis stay unchanged.

**How the parts are built (step 3.9, `src/io/legacy-v6/id-parts.ts`, `id-space.ts`).**
- *Hash*: the deterministic core `hash64` (`src/core/hash.ts`, step 2.2), its first 6 hex characters, of the ORIGINAL value (§4.2 names no other function).
- *Sanitising*: ASCII letters are lowercased, digits and `-` kept, every other code point (one per code point, not per UTF-16 unit) becomes `-`; `Ab.c` gives `ab-c-<hash6>`, an unchanged `c15` stays `c15`, an empty ID gives `-<hash6>`.
- *Length*: an ID body is at most 63 characters, so a part is capped at 27 characters. A longer value is truncated (to 20 characters plus `-<hash6>`); truncation counts as "sanitising changed the value", so the hash of the whole original is always there.
- *Text-derived parts* (`l-<slug>-<hash6>`, `cpt_v6-<slug>-<hash6>`, …): the key is the FOLDED text (`fold`, core), so labels that fold alike share one record; the slug is the folded text's `[0-9a-z]` runs joined by `-`, at most 40 characters (empty slug: the hash alone); the hash is `hash64` of the folded text. Matching text against existing records is step 3.10/3.11.
- *`rel_v6-<lower>-<higher>`*: "lower" is the smaller of the two legacy reaction IDs in plain code-unit order (`r12` before `r3`); a reaction related to itself has no relationship.
- *Collisions inside one document* (two different originals with one part: a hash collision, or an original that already looks like a produced part, such as `c15!` and `c15--<its hash>`): never merged. The whole document is settled at once, per namespace (compound, reaction, label, concept, named reaction, topic, relationship): every colliding original moves to a 12-character hash, then a 16-character hash, then `<hash16>-<n>`, repeating until all parts are unique. The result does not depend on the order of the input. Each collision is returned in `collisions` for the import report. Consequence, stated: the IDs of the colliding values differ from what a document without the collision would give them.
- *One pass for namespaces that share an ID family (step 3.10 review)*: a compound part is the body of `spc_v6-…`, `cls_v6-…`, `anc_v6-…` and `edp_v6-…`, a functional-group part of `cls_v6-fg-…`, a `compoundClass` text part of `cls_v6-l-…`, a label part of `spc_v6-l-…` and `rgt_v6-l-…`. The compound, functional-group, class-text and label namespaces are therefore settled in ONE pass in which two values collide when they would produce the same ID body in the same family (`spc` or `cls`). A crafted clash (a hub with id `fg-x` against the functional-group class of `x`; an `l-…` compound ID against a text class or a label species) is settled by the ladder above like any other, reported in `collisions` (namespace `compound+functional_group`, …) and never refused; both values get a longer hash, and a compound keeps ONE part for all its prefixes. A label and a class text that fold alike share no family and do not collide. Without such a clash every ID equals the tier-0 part above, byte for byte. The mapper's `DUPLICATE_RECORD_ID` refusal remains only as a last-resort guard and is not reachable from any input tried (property test over crafted IDs).
- Every generated ID is tested against the schema's ID pattern of its kind, including for arbitrary strings.
- *Registration (step 3.10, `id-collect.ts`)*: `createDocumentIds(data)` registers EVERY value before anything is mapped: the IDs of all compounds and of every compound only a reaction refers to (a dangling ref), all reaction IDs, the remainders of label-only participants after the label parser (a whole-label temperature is not a label), concept texts (`reactionType`, `reactionFamily`, `mechanism.type`, `jee.prerequisites`, `jee.concepts`), named-reaction texts, topic texts (`chapter` except `Uncategorised`), related pairs whose two reactions exist, functional-group ids and `compoundClass` texts (step 3.11b adds the `transformationKey` of every reaction whose `transformation.fgFrom` / `fgTo` hold at least one non-blank id). A hub's decision is not known yet, so the set is a superset of what is used. A record's key in the ID space is its legacy ID as text (a non-text ID by its JSON); a REPEATED ID is never merged: the first record keeps the key, the n-th later one gets `<id>\u0000<n>`, which the sanitiser turns into a different, hash-carrying part (`spc_v6-c1-2-<hash6>`); references resolve to the first, as v6's own lookups do.

**Records without an `id`** (v6 would draw a random one) are never refused. The port (step 3.8) assigns the deterministic placeholders `c-missing-<n>` (compound) / `r-missing-<n>` (reaction), `n` = the first free number counting from the record's position, and lists them in `assignedIds`. From then on they are ordinary legacy IDs: they map through the table above like any other (`spc_v6-c-missing-3`, `rxn_v6-r-missing-1`; they need no hash suffix because they are already `[0-9a-z-]`). Every such record is a REVIEW REQUIRED item (§4.7).

### 4.3 Pipeline

1. **v4 → v5 normalisation**: a TypeScript port of v6's `migrateLegacy`, `splitLegacyReagent` and `normalizeData`, including their quirks. Its output must deep-equal the oracle fixture. Porting the legacy behaviour first means v4 data is interpreted exactly as the user saw it in v6. Implemented in `src/io/legacy-v6` (step 3.8) as `normalizeLegacyData(raw)`: it deep-equals the oracles for `v4-sample.json` and `v6-demo-export.json` and for a quirk workbook (`tests/fixtures/legacy-v6/`), all produced by v6's own code (`scripts/legacy-oracle.mjs`). Three things v6 does not do, all reported and never silent: (a) it returns `dropped`, the leaves of the input the v5 output does not hold verbatim (path → value; empty for both fixtures; e.g. v6 overwrites a non-boolean `collapse`, ignores a `mech` next to a `mechanism.summary`, deletes v4 keys from a v5 reaction and rebuilds participants from six known fields), which step 3.11's completeness test carries into `provenance.legacy.unmapped`; (b) a record without an `id` gets a deterministic placeholder (`c-missing-<n>` / `r-missing-<n>`, listed in `assignedIds`) instead of v6's `Math.random`; (c) input v6 would throw on or build garbage from (a document or record that is not an object, a compound without a text name that a reagent name has to be matched against) is refused as a value (`NOT_AN_OBJECT`, `INVALID_RECORD`, `INVALID_COMPOUND_NAME`) with the path. Quirks kept: migrated v4 participants carry no `image` (so v6 is not idempotent on its own v4 output: a second pass adds `image: ""`), role names that are inherited object keys count as roles, an unrecognised `nodeType` becomes `auto`, `Object.assign` copies of `conditions`/`transformation`/`mechanism`/`jee` keep unknown fields while participants do not.
2. **v5 → ORN mapping** (§4.4–§4.6) producing a `DatasetDocument` plus a `LegacyImportReport`.
3. The normal import pipeline (PERSISTENCE.md §6): quarantine, conflicts, merged-replica validation, **preview with decisions**, snapshot, one atomic apply.

**How step 3.11c wires it (`src/io/import-legacy.ts`, `import-session.ts`).** `legacy_v6` / `legacy_v4` are no longer refused: `ImportSession.preview` and `revise` (now async, because image hashing is) call `convertLegacy` on the parsed payload on every preview and revise: port (3.8) → ID space (3.9) → compounds (3.10) → reactions (3.11a) → classification (3.11b) → strict L1 of every mapped record (a failure would be quarantined, never dropped) → an `ImportParseResult` that the normal pipeline takes over (per-record quarantine, conflicts, merged replica, validation, preview). The clock is the injected `IdFactory.now()`; the `LegacyMatchContext` is built from the LIVE state at preview time (`matchContextFromRecords`; the revision checks already refuse an apply on a stale preview). Legacy image bytes are `ParsedAsset`s and take the same `AssetStagePort` path as `.ornpkg` bytes.
- *Preview decisions* (`ImportPreview.decisions`, requested through `ImportPlanRequest.decisions: { id, chosen }[]`; legacy imports only): `hub:<hub key>` (options `class` (default), `species`; the subject is the hub's record under the current choice) and `reagent_family:<value>` (one per distinct value; the subject is the first reaction that carries it). A changed decision is a `revise` with the FULL request (a new `batchId`, the old batch is gone; a decision left out returns to its default); an unknown decision or an option it does not have is `INVALID_REQUEST`; `apply` refuses a plan whose decisions differ from the previewed ones (`PLAN_MISMATCH`, decisions are part of the plan identity). **`reagentFamily` has only the option `keep`**: the schema has nowhere to put it (a reaction has no family field; `Reagent.families` is a fixed vocabulary and `Reagent.classIds` belongs to a reagent record shared by many reactions, while a reaction's `reagentFamily` does not say which of its reagents it describes), so the value stays in `provenance.legacy.unmapped`; no field is invented. Defaults are non-destructive and every decision taken is in the batch report.
- *The full `LegacyImportReport`* (`ImportPreview.legacyReport`, stored in `ImportBatchReport.legacyReport`): created counts per kind, every review item with its reason, `preservedUnmappedFields`, `consumedByDefault`, `notes`, `documentUnmapped` (the preview must show it: it is persisted only inside the batch report), the ID-space `collisions`, `unsafeKeysRenamed` (from the io parse), the `decisions` taken, `reagentFamilies`, `notImported` (expected empty). Plain JSON: structured-clone- and JSON-safe.
- *Re-import*: importing the same file with the same clock resolves every record as `identical_skip`. To make that true the classification step never treats a record this import would create itself (same deterministic ID) as a match in the live dataset: the record is created again, identical. With a DIFFERENT clock the only fields that differ, on every record, are `provenance.createdAt` and `provenance.updatedAt` (the legacy file carries no time), so nothing is recognised as identical and the default resolution is `keep_current`.

**How step 3.10 reads the table (`compound-map.ts`, `compound-convert.ts`, `compound-classes.ts`, `compound-records.ts`).**
- *One rule for every text field*: a legacy value the target field's schema accepts as it stands is stored verbatim (no trimming, no repair: `"  Ethanol "` stays); an empty one stores nothing; a value that does not fit (too long, control characters, wrong type) or that the target has no field for is kept whole in `provenance.legacy.unmapped` under its legacy key (`jee.level` as `{ jee: { level } }`), counted in `preservedUnmappedFields`, and gets a review reason where a person must decide. A name that cannot be stored becomes `Unnamed legacy compound #<position>` with the original in `unmapped.name` and a review reason.
- *Hubs*: the decision "class (default) / species" is an input (a Map keyed by the hub's key); both paths are built. A class hub gets `generic.formulaText` (from `genericFormula`), `description` (from `properties`), `studyNotes` (from `jee.notes`), `tags`, and its image as an asset; every other hub field (`smiles` with the reason above, `formula` when it repeats `genericFormula` (else it is the class's `generic.generalFormula`, with a review reason), `acidBase`, `aromaticity`, `stereo` with its reason, `fgId`, `functionalGroups`, `compoundClass`) is kept in `unmapped`: a class has no field for them, and the last three describe the hub itself (a class is not a member of a class). A hub decided as species is an ordinary species (its SMILES is its structure) whose anchor targets the species; its review says "hub treated as a species by decision". The anchor's `order` is the hub's 1-based position among the hubs in file order. `node: false` (hub or not) adds an `entity_display` with `showAsNode: never`.
- *Species* get `speciesKind: unspecified`, `structure` from `smiles`, `formula`, `notes` from `properties`, `acidBaseNotes`, `aromaticity` only for the exact strings `aromatic` / `non-aromatic` / `antiaromatic` (case-sensitive; anything else non-empty is kept + review), `stereo` `{ kind: unspecified, descriptors: [], note: <text> }` + review, `studyNotes` from `jee.notes`, `tags` (the ones that fit `TagSchema` and the first 64; the rest kept + one review reason). `genericFormula` on a species and `nodeType` `branched` / `sub` are kept, no review (a v6 view hint).
- *Membership* (species only): all functional groups of the document are settled first, then all `compoundClass` texts, so the result does not depend on the order of the records. `fgId` and each `functionalGroups[]` entry name the hub class (decided as class) whose own `fgId` is that id (two hubs: the first, with a review reason), else a `functional_group` class made once per id from the legacy registry label (an id v6 does not know: from its own text), review reason on the class. A `compoundClass` text names the class with that folded name (hub classes and the classes made above), else a `compound_class` is made from the text, review reason on the class. Created classes and imported compounds are `published` (the record is complete); created classes are also `review_required` (nobody has checked them), as §4.5's lifecycle row does for reactions. A published species that lists a created class therefore raises no RVW-002 finding. At most 256 classes per species; the overflow is kept + review.
- *Review reasons* are one per cause and per record (unknown fields, dropped values and tags are grouped into one reason each); a record carries at most 32, the rest is summarised in the last reason and every reason is a `reviewItems` entry of the report. Duplicate folded names are reported per output kind (species with species: SPC-001; classes with classes, created ones included: CLS-002); a species and a class that fold alike are not (SPC-005 is a validation INFO). An ID collision (§4.2) is a reason on the records that were moved.
- *Images*: `data:image/png|jpeg|webp|gif|svg+xml;base64,…` only, padded base64, bytes matching the media type (magic bytes) and at most 20 MiB: decoded, hashed, one asset per sha256 (attached to every compound carrying it, at most 64), bytes carried in `assetBytes` for the import pipeline. Anything else (a URL, another encoding, damaged data, a 65th attachment) is kept in `unmapped.image` with a review reason; it is not in `notImported` (the value is preserved).
- *Refusals* (values, nothing is mapped and a shared report is left untouched): `INVALID_CLOCK` (the injected clock did not return a UTC ISO timestamp) and `DUPLICATE_RECORD_ID` (two records of the mapped compounds got one ID: a last-resort guard; the shared collision pass of §4.2 settles the clashes of crafted IDs, so no known input reaches it).

| `namedReaction` | named reaction matched by folded name/alias or created → `namedReactionIds` |
| `chapter` | topic matched by folded name/alias in the curriculum tree, else created as a chapter (review) → `topic_mapping (core)`; "Uncategorised" → no mapping |
| `jee.relevance` both / main / advanced | `exam_relevance` for JEE Main and/or JEE Advanced, scope `official`, all versions, **review** ("imported flag, not verified against a syllabus") |
| `jee.difficulty` 1–5 / 0 | `difficulty` / absent |
| `jee.traps[]` | one `caveat` (`trap`) per entry targeting the reaction |
| `jee.prerequisites[]`, `jee.concepts[]` | concepts matched/created → `prerequisiteConceptIds`, `conceptIds` |
| `relatedReactions` | `related_to` relationships (one per unordered pair) |
| `collapseIntermediates`, `_v4` audit trail | `legacy.unmapped` |
| `image` | asset attached to the reaction |
| `scope` | `specific` if every substance ref is a species, `generic` if any is a class; mixed → `generic` + review (RXN-022) |
| lifecycle | `published` if RXN-001/002 pass, else `draft`; status `unreviewed` unless a review trigger fired |

**How step 3.11a reads the table (`reaction-map.ts`, `reaction-participants.ts`, `reaction-roles.ts`, `reaction-labels.ts`, `reaction-substances.ts`, `reaction-conditions.ts`, `reaction-assets.ts`).** This step maps `id`, `name`, `tags`, `participants`, `conditions` and `image` of a reaction. `transformation`, `mechanism`, `reactionType`, `reactionFamily`, `reagentFamily`, `namedReaction`, `chapter`, `jee`, `relatedReactions`, `collapseIntermediates` and `_v4` are step 3.11b: the mapper returns every leaf under them as a `deferred` path (never mapped, never skipped silently); any other unknown reaction field is kept in `legacy.unmapped` with a review reason. Dropped leaves of the v4 → v5 port outside compounds are handed on unchanged (`unhandledDropped`) for 3.11b.
- *Roles*: as the table says. Reagent-like roles (for a label-only participant that needs a record) are `reagent`, `catalyst`, `solvent`, `spectator` and `workup`; substance roles are `substrate`, `reactant`, `product`, `byproduct`. A role that is not one of the ten v6 roles (v6 counts inherited object keys such as `toString` as roles) is imported as `reagent`, v6's own default, with the original role in `unmapped` and a review reason. Several `major` products are all `main`; a `major` flag on a non-product is kept in `unmapped`. A coproduct or byproduct that points at a class also gets the reason "a specific species may be intended" (§4.9 r18). The same substance twice with the same role (§4.9 r12) is a review reason and is kept, never merged (validation reports RXN-021).
- *One outcome*: `out_v6-<r>-1`, all products, `selectivity: unspecified`, no condition variants; none when the reaction has no product. Reversibility is `unknown` (v6 has no such datum).
- *Intermediates*: `intermediateKind: other`, review. A participant with a ref keeps the ref; a label-only intermediate keeps its label as the intermediate's `label` (a name for a transient species: no species record is created for it, unlike other label-only participants).
- *References*: a `ref` resolves through the compound mapper's reference map, so a hub decided as class is referenced as the class and a hub decided as species as the species. A ref no compound has creates ONE placeholder species "Missing legacy compound <id>" per missing ID (draft, review), shared by every reference. A label-only participant is matched by folded name against the mapped compounds (species first, then classes, file order; several matches use the first and say so), then against the records this run already created from labels, else one record per folded label is created (reagent for reagent-like roles, species otherwise; a product only ever refers to a species or class, so it never reuses a created reagent). Created-from-label and created-class records are `published` + `review_required`, placeholders `draft` + `review_required`. A label of tokens only (`dry`) keeps the label itself as the name and takes no token out; a label that cannot be a record name or original text, and a participant with neither ref nor label, is kept whole in `legacy.unmapped` with a reason (nothing is dropped). Matching against the user's live dataset is NOT done here: the import pipeline's conflict analysis handles IDs.
- *Stage parameters from labels*: a whole-label temperature or light goes to stage 1 (stage 2 for a `workup` participant) with `parsedFields`; when the stage already has a different value for the field (from `conditions`) the label goes to that stage's `other[]` as `temperature: 443 K` with a reason.
- *Conditions*: stage 1 `parameters` from the step 3.9 parser, `conditions.text` as `parameters.text` and the stage's `originalText`; non-empty `parsedFields` add the RXN-015 review reason; parser review items become reasons; `FLAG_SUBSUMED` notes are counted in the report's `notes`; a value the parser could not read (wrong type, non-boolean flag, blank text, a text the schema cannot hold), an unknown `conditions` key and `other[]` entries beyond the schema's 16 are kept in `unmapped` (`unmapped.conditions.<key>`, `unmapped.conditions.overflowOther`).
- *Notes and images*: a participant `note` is the participant's, product's or intermediate's `note`. A participant image and the reaction image become assets attached to the REACTION; the attachment's note is the participant's label (else its ref text). Same decode, hash, ID and cap as compound images (`legacy_image`): an image a compound also carries is ONE asset with several attachments (the reaction mapper returns a changed copy in `updatedAssets`; `mergeMappedRecords` puts it in place of the compound mapper's record). An undecodable image stays in `unmapped` with a reason.
- *Scope*: the species and class references of participants, products and intermediates (reagent references do not count): a class among them → generic, else specific; species and class together → generic + the mixed-scope reason. *Lifecycle*: `published` when there is a reactant participant and an outcome with a product (RXN-001/002), else `draft` with the reason; status `review_required` exactly when the reaction has reasons.

**How step 3.11b reads the table (`classify-map.ts`, `classify-fields.ts`, `classify-jee.ts`, `classify-book.ts`, `classify-transformations.ts`, `classify-scope.ts`, `match-context.ts`, `exam-vocab.ts`).** `mapLegacyClassification` takes the port's `data`, the ID space, the 3.10 compound result, the 3.11a reaction result (the eleven fields it returned as `deferred`, and `unhandledDropped`) and an optional `LegacyMatchContext`; it returns the 3.11a reactions completed (changed copies: same IDs and order, the 3.11a record is never mutated) plus the new records, and its own `deferred` / `unhandledDropped` are the LEFTOVERS, which stay empty. Every rule of §4.4-§4.5 that holds for all fields holds here: an empty value is consumed and stores nothing; a value the target accepts is stored verbatim (no trimming, no clamping, no repair); a value it does not accept, or that has nowhere to go, is kept whole in `provenance.legacy.unmapped` with a review reason where a person must decide.
- *Match context (decision)*. `LegacyMatchContext { records: { id, kind, names (folded), parentId? (topics), conceptKind? (concepts) }[] }` is plain, read-only data listing the LIVE dataset's concepts, named reactions, topics and exams; it is optional and defaults to empty (a fresh dataset). `matchContextFromRecords` builds it from records; candidates for one name are ordered by record ID, so the output does not depend on the order the context lists them in. Concepts, named reactions and topics resolve in this order: (1) a context record with that folded name or alias; (2) a record this import already created for that folded text (one record per folded text, the ID space keys them so); (3) a new record, `published` + `review_required` (created concepts / named reactions / topics are §4.7 triggers). Several context matches: the first by ID, and the reaction carries a review reason saying so (for topics a match that has a parent, i.e. a chapter under a subject, is preferred to a root topic of the same name). Concepts are matched WITHIN their kind for the three kind-specific roles (`reaction_type`, `mechanism_class`, `reaction_family`); a dataset concept of another kind with that name is not reused there, and the new record says so; the `general` kind (prerequisites, concepts) reuses a concept of any kind. One text under two kind-specific roles is TWO concepts, one per kind (step 3.11b review; this supersedes the first 3.11b rule "one record, the first role names its kind"); a generic role reuses a concept of that name of any kind. Exams are NEVER created.
- *Transformation*. `from` / `to` → `generalizedEquation` (`from → to`; `from` alone; `→ to` for `to` alone; both empty: none; a half longer than about 1,000 characters is kept). `fgFrom` / `fgTo` are functional-group ids: each becomes the class step 3.10 made for it (`functionalGroupClass`), else the first hub decided as class with that `fgId`; an id with no class stays in `unmapped` with a review reason (no class is invented). The FROM and TO class sets (sorted, repeats collapsed, `FG_REPEATED_IN_SET` note) match a transformation created earlier in this import, else a new `transformation` record is created (published, `review_required`; named from the class names). At least one class is needed for a record; `bondChanges` is its `bondChangeSummary`: the first non-empty text stays, a different text on a later reaction is kept in that reaction's `unmapped` with a reason, and a text with no transformation record to belong to is kept with a reason.
- *Mechanism*. `type` → a `mechanism_class` concept → the reaction's `mechanismClasses` with certainty `probable`; `summary` → a `mechanism` record (`Mechanism of <reaction name>`, the summary, the same classes, NO variants: validation says MEC-001, an INFO) referenced by `mechanismIds`. A whitespace-only summary or a type the schema cannot name is kept.
- *reactionType* → a `reaction_type` concept → `reactionTypes` (certainty `definite`: v6 states it plainly; §4.5 names a certainty only for `mechanism.type`); *reactionFamily* → a `reaction_family` concept → `conceptIds`; *namedReaction* → `namedReactionIds`.
- *reagentFamily*: kept in `unmapped` on every reaction that has one (no review reason: nobody can decide it here), and `mapLegacyClassification` returns the DISTINCT values with the number of reactions that carry them (`reagentFamilies`, sorted by value, exact text); step 3.11c turns them into preview decisions.
- *chapter*: "Uncategorised" (exactly, quirk r22) → nothing (no topic, no mapping, nothing kept); any other name → a topic (context match, else created at the root as a `chapter`, `order` = its creation number) and one `topic_mapping` per reaction (`tmp_v6-<reaction part>`, role `core`).
- *jee*. `relevance` `both` / `main` / `advanced` (exact) → `exam_relevance` for the matching exam(s) of the context (matched by folded name; `exam-vocab.ts` holds the v6-value → exam-name table as legacy-format vocabulary), scope `official`, no version (all versions), `review_required` with "imported flag, not verified against a syllabus"; an exam the context lacks is not created: the value stays in `unmapped` with a review reason and the exam that exists still gets its record. An unknown word is kept with a reason. `difficulty` 1-5 → `difficulty`; 0 → absent (consumed); anything else is kept with a reason. `traps[]` → one `caveat` (kind `trap`, `cav_v6-<r>-<n>`, `n` = the position in the list; the title is the text when it fits a label, else `Trap <n> of reaction #<position>`; the statement is the whole text; the target is the reaction as `affected_reaction`). `prerequisites[]` / `concepts[]` → `general` concepts → `prerequisiteConceptIds` / `conceptIds` (repeats collapse with a `CONCEPT_REPEATED_IN_LIST` note; more than 256 are kept, never cut).
- *relatedReactions*: one `related_to` relationship per unordered pair of EXISTING reactions (`rel_v6-<lower>-<higher>`, `from` = the lower legacy ID, whichever reaction lists the other or both do; a reference resolves to the FIRST reaction with that legacy ID, as v6 does). An ID that names no reaction is kept in `unmapped` with a review reason and no placeholder reaction is made; a reaction listing itself makes no relationship and keeps the entry with a reason.
- *collapseIntermediates*, *`_v4`*: kept whole in `unmapped`, no reason. Unknown fields under `transformation`, `mechanism` and `jee` are kept with one reason per block.
- *Dropped leaves (§4.8)*: see there. *Not built*: exam versions, syllabus checks, matching against anything but the injected context (the import pipeline's conflict analysis handles IDs, §4.3 step 3).

### 4.6 Label parser

Tokens are removed from a participant label into structured fields; `originalText` always keeps the untouched label.

| Token | Field |
|---|---|
| `aq.`, `(aq)`, `(aq.)`, `aqueous` | `phase: 'aq'` |
| `alc.`, `alcoholic` | `phase: 'alc'` |
| `conc.`, `concentrated` / `dil.`, `dilute` / `fuming` / `glacial` / `sat.` | `strength` |
| `dry`, `anhydrous` | `dry: true` |
| `(excess)`, `excess` | `quantity.qualifier: 'excess'` |
| `(cat.)`, `catalytic` | `quantity.qualifier: 'catalytic'` |
| a whole label that is a temperature (`443 K`, `140°C`, `0-5 °C`) | not a participant: moved to the stage's `temperature`, added to `parsedFields` |
| `hv`, `hν`, `light`, `UV` as a whole label | moved to `light` in stage parameters |

Step 3.9 (`label-parser.ts`) reads the table as follows. Matching is case-insensitive and by whole word (`dry` is not taken out of `drying agent`); `aq`, `alc`, `conc`, `dil` are also accepted without the dot (as v6's own regexes do), and `saturated` next to `sat.`; the parenthesised form of any LISTED token is also accepted (`(aq)`, `(aq.)`, `(excess)`, `(cat.)`, `(conc.)`); other parenthesised text is never a token (`(ice bath)`, `(2 eq)` stay in the remainder untouched). `non-aqueous` is not `aqueous` (left in the label, reported). Two tokens that disagree on one field (`aq. alc. KOH`) are none of them taken out and the label is reported; a label of tokens only keeps an empty remainder and is reported; a temperature inside a longer label (`H2SO4, 443 K`) is not split off (reported). A whole label that is a temperature (units K and °C, ranges with hyphen or en-dash) or `hv`/`hν`/`light` (→ `light: hv`) / `UV` (→ `light: uv`) is a stage parameter; a whole label that is clearly a temperature but not storable (`100 °F`, `5-0 °C`) is a stage parameter in `other[]`, reported. The result always carries `originalText` and `segments` that tile the label exactly, so no character is lost.

The remainder is matched against existing reagents/species by folded name or alias (so "aq. KOH" and "alc. KOH" both resolve to the single reagent **KOH** with different phases). Unmatched remainders create one shared record per folded label, `review_required`.

### 4.7 REVIEW REQUIRED triggers (never silent)

Hub representative SMILES; hub treated as species by decision; created-from-label records; missing compound placeholders; non-major products; intermediates; parsed conditions; created concepts/topics/named reactions/transformations; imported exam relevance; mixed-scope reactions; duplicate folded names; unrecognised aromaticity or stereo text; undecodable images; any unsafe key renamed; a record that had no id in the legacy file (placeholder `c-missing-<n>` / `r-missing-<n>`, §4.2).

### 4.8 No-loss guarantee

A leaf that the v4 → v5 port reports as `dropped` (step 3.8) follows a fixed rule: a dropped leaf whose value is empty (`""`, `[]`, `{}`, `null`) and was replaced by a default counts as **consumed by default** and is counted per path in the report (`consumedByDefault`, path → occurrences); any dropped leaf with content is stored in the record's `provenance.legacy.unmapped` and raises a review item. (`dropped` itself stays strict: it lists both kinds and the split happens in the mapper.) Step 3.10 does this for every dropped leaf under `compounds[i]`: an empty one (`""`, `null`) is counted under its path with every index written `[*]` (`compounds[*].tags[*]`); one with content is kept in the record's `provenance.legacy.unmapped.dropped` under its path inside the compound (`"functionalGroups[1]"`), counted in `preservedUnmappedFields` as `dropped.<path with [*]>`, with one review reason per record. Dropped leaves outside the compounds (reactions, top level) are returned untouched (`unhandledDropped`, also on the step 3.11a result) for step 3.11b. Step 3.11b applies the same rule to every dropped leaf under `reactions[i]`: an empty one is counted under its path with every index written `[*]` (`reactions[*].jee.concepts[*]`); one with content is kept in the reaction's `provenance.legacy.unmapped.dropped` under its path inside the reaction (`"jee.difficulty"`), counted in `preservedUnmappedFields` as `reaction.dropped.<path with [*]>`, with ONE review reason per reaction (a reaction with an unknown legacy field that is itself called `dropped` keeps it there; the port's leaves go under `dropped#3.11b`, nothing is overwritten). A value that belongs to the DOCUMENT and to no record (a top-level field next to `compounds` and `reactions`, a dropped leaf whose path names no record such as the original top-level `schemaVersion: 4`) goes to `LegacyImportReport.documentUnmapped` (top-level key, or `dropped.<path>`, mapped to the value verbatim), is counted in `preservedUnmappedFields` as `document.<key>` and in `notes` as `DOCUMENT_VALUE_KEPT`; empty ones are consumed by default. It raises no review item (there is no record to review); the report lists it, and `notImported` stays empty. After step 3.11b nothing is deferred and `unhandledDropped` is empty.

A completeness test walks every leaf of the legacy JSON and asserts it is either consumed by a mapping (the mapper records a trace of consumed paths) or present in some record's `provenance.legacy.unmapped` (INV-23). The report lists created counts, every review item with its reason, preserved unmapped fields with occurrence counts, `consumedByDefault`, informational `notes` by code (for example `FLAG_SUBSUMED`; never review items), and `notImported` (expected empty; each entry explains why). `notImported` lists ONLY values that are preserved nowhere; a value kept in a record's `provenance.legacy.unmapped` is preserved, so it is counted in `preservedUnmappedFields` and never listed in `notImported` (an undecodable image is the example: kept in `unmapped.image`, reviewed, not in `notImported`).

### 4.9 Known quirks in real v6 data (from the fixtures)

- Hubs carry example structures: Alkanes `CCCC`, Alkenes `C=CC`, Arenes anthracene, Alcohols `CCO`, Ketones acetone.
- `r12` lists Alcohols as both substrate and reactant → two reactant participants referencing one class (RXN-021 warning, review) — kept, not merged.
- `r14` ester hydrolysis produces the specific species palmitic acid from the generic class Esters → mixed scope, review.
- `r18` cumene process links its acetone coproduct to the Ketones hub → coproduct points at a class, review suggests a specific species.
- v4 reagent strings like `conc. H2SO4, 443 K` made v6 store "443 K" as a *reagent* label; the label parser moves it to temperature.
- `r22` is an unanchored test reaction with chapter "Uncategorised" and no relevance → imported without topic or exam mapping, visible in the Unanchored list.
- v6 condition flags were inferred by regex; all of them become `parsedFields`.
