# Persistence, Import/Export and Recovery

Package sections: **#14 Persistence**, **#15 Import/Export**, **#22 Error Recovery** (with ARCHITECTURE.md §22). Contracts: `src/persistence/contracts.ts`, `src/io/contracts.ts`.

## 1. Principles

1. IndexedDB (via Dexie 4) is the on-device store of record. Nothing canonical lives in localStorage, cookies or the URL.
2. Every IndexedDB transaction is atomic and ends on a committed revision (INV-20): an idle queue writes one transaction per ChangeSet; ChangeSets queued together may share one transaction that ends on the newest of them. Partial writes are impossible.
3. Memory is authoritative while the app runs; persistence follows through a serial queue. A failed write never loses the in-memory state and is always visible.
4. Imports, migrations and restores are previewed, snapshotted, and applied atomically (INV-21).
5. Exports are deterministic (INV-19) and self-describing (format + schemaVersion).

## 2. Storage layout

Database `orn`, Dexie version `DB_VERSION` (starts at 1). Store definitions live in `DB_STORES`; changing them requires a version bump, an upgrade function, and an upgrade test using fake-indexeddb.

| Store | Key | Contents |
|---|---|---|
| records | `id` (index `kind`) | Every canonical record, one row per record, exactly as the schema defines it |
| meta | `key` | `schemaVersion`, `datasetMeta`, `revision`, `lastCleanShutdownAt` (a time, or `null` while a session runs), `lastIntegrityCheckAt` |
| assetBlobs | `assetId` (index `sha256`) | Image bytes as Blob |
| snapshots | `id` (indexes `createdAt`, `reason`) | The summary fields (`id`, `createdAt`, `reason`, `revision`, `schemaVersion`, `byteSize`, `note?`) plus the fflate-compressed DatasetDocument JSON as a Blob (so listing rows does not load the bytes) |
| editorSessions | `id` | Authoring drafts (may be invalid) for crash recovery |
| derivedCache | `key` (indexes `cacheKind`, `lastUsedAt`) | Depictions, layouts, search index, structure facts; `{ key, cacheKind, value, byteSize, lastUsedAt }`; LRU-evicted, disposable |
| uiState | `key` | Selection, viewports, expansion, panels, active exam version; tolerant parsing |
| importBatches | `id` | Import reports (what was created, decisions made) |
| quarantine | `id` | Records that failed validation at boot or import, with issues |

A generic records table (rather than one store per kind) keeps schema evolution in Zod migrations instead of IndexedDB upgrades, and makes transactions over mixed kinds trivial.

The in-memory `CanonicalState` is `{ meta, records: { [kind]: { [id]: record } } }`, frozen by Immer. The file format is `DatasetDocument` (`src/core/schema/dataset.ts`): `{ format: 'orn.dataset', schemaVersion, exportedAt, exportScope, generator, meta, records: { [kind]: record[] } }`.

## 3. Write path

```
dispatch(envelope) ─► commit (memory, revision n) ─► ChangeSet n
      └─► persistence queue (serial)
             └─► tx(records, meta): put created+updated, delete deleted, meta.revision = n
                    ├─ ok       → SaveStatus.saved (lastSavedRevision = n)
                    └─ failure  → retry 250 ms, 1 s, 4 s → SaveStatus.failed (banner, "Export now")
```

- An idle queue writes one transaction per ChangeSet. ChangeSets that wait together are coalesced: the queue remembers WHICH records they touched and the newest state, so the latest value wins (delete then create = put; create then delete = delete). One transaction then moves the database from one committed revision straight to the newest. It is still one atomic transaction (INV-20): never a partial ChangeSet, and the database never holds a state memory did not have. ChangeSets committed in the same tick share a transaction.
- A failed write is retried after 250 ms, 1 s and 4 s, then the state is `failed`. The pending ChangeSets are **kept**: the next ChangeSet, or `flush()`, starts a fresh cycle over everything pending, so no revision is ever skipped. A ChangeSet whose revision does not follow the previous one is refused loudly (status `failed`, an exception): the database would miss that change for good.
- `writeChanges(changes, next, blobs?)`: the bytes of asset records created in that ChangeSet ride in the same transaction (§5). The promise resolves when the write cycle holding the ChangeSet ends, durable or `failed`; `getStatus()` says which.
- Every other IndexedDB write (the clean-shutdown and integrity-check markers, snapshots) goes through the same queue and runs in its order, after the ChangeSets pending when it was requested (`runOrdered`); it never changes `SaveStatus`, and it is refused on a read-only tab. **The single exception is `derivedCache`**: it is disposable and never canonical, so cache puts and gets bypass the queue (a failed cache write is a value, never a SaveStatus problem). The caller of `setLastCleanShutdownAt` still checks `getStatus()` first.
- `SaveStatus` is always visible in the status bar: saved / saving / retrying / failed / read-only. `getStatus()` is synchronous: writes are pending when `pendingRevisions > 0` or the state is saving, retrying or failed; on `beforeunload` with pending writes the app warns.
- Undo and redo are ordinary commits and persist the same way.

## 4. Boot sequence

`adapter.open()` runs it once and returns an `OpenResult` (`src/persistence/boot.ts`); its parts are pure or take the adapter's ports (`boot-load.ts`, `boot-migrate.ts`, `boot-checks.ts`). Boot takes an injected `WriterLock` (`createWebLocksWriterLock` in the app) and an injected `MigrationRunner`; the same sequence runs again as the writer when a follower is promoted (§10). Every branch that cannot make the data writable leaves the queue read-only and writes **nothing**.

1. Open the database; run Dexie upgrades if `DB_VERSION` increased. IndexedDB missing, refused or out of quota → `mode: 'unavailable'` (session-only mode; `reason` and `detail` say why).
2. Acquire the writer lock `orn-writer`. Not granted → open **read-only**, load the state, write nothing (no quarantine rows, no markers), follow changes (§10). If the stored data then needs a migration, only the writer may run it: the tab opens read-only without data and loads when the writer's migration message arrives. `unsupported` (no Web Locks): the tab is the writer and `bootReport.singleTab` is set.
3. Read records and meta in one transaction, then look at `meta.schemaVersion`:
   - newer than the runner's target → read-only, `readOnlyReason: 'newer_schema'`, `state: null`, `detail` explains ("Data was saved by a newer version"), the lock is released, nothing changed;
   - anything else that is not the current version goes to the runner, in memory, before anything is written. A version the runner refuses outright (0, negative, non-integer, not a number, missing next to stored records) → read-only `migration_failed`, nothing written, no snapshot. An older version: `pre_migration` snapshot of the stored rows exactly as they are (raw, not validated: they are in the old shape) → the migrated document → strict parse → L1–L3 (`validateAll`, no ERROR) → `replaceAll` at `revision + 1`. Any failure after the snapshot puts the stored rows back from that snapshot, opens read-only with `readOnlyReason: 'migration_failed'` and keeps the error detail. The undo history starts empty (the store is built afterwards);
   - a current version with a missing or invalid `datasetMeta`, or a missing or invalid `revision`, is `integrity_failure`: read-only, `state: null`, nothing written.
4. L1-parse each row. A row that fails L1 (or has no known kind) is left out of the state and **moved**: the writer removes it from `records` and writes its `quarantine` row (the issues and its FULL raw value, exactly as stored, no cap, §7) in ONE transaction through the queue's ordering (`runOrdered`). `records` must always equal the in-memory state: were the row only copied, `replaceAll`, a restore or a recovery would later delete a row that was only ever kept there. One transaction also means a crash between the two steps is impossible. The quarantine ID is derived from the row's ID; the row is gone from `records`, so the next boot does not quarantine it again. A quarantine row already stored under that ID (a copy from an earlier version) is kept if its raw value is the same, replaced by the full value if it is a truncated copy, and a different value is stored under its own ID (a hash of the value is appended): nothing stored is ever overwritten with less. A tab without the lock leaves such rows out of its state and writes and moves nothing.
5. Build indexes; run `validateAll` (the findings are returned in the `bootReport`, so the store need not run it again); report asset records whose bytes are missing from `assetBlobs` (AST-002); restore uiState tolerantly (an entry that is not plain JSON, or fails the caller's validator for its key, is reset and reported, never a reason not to boot).
6. Crash check: `meta.lastCleanShutdownAt` is `null` while a session runs (boot writes `null` once it has read the previous value) and a time after a clean shutdown; a `null` (or unreadable) value at boot means the previous session did not shut down cleanly, and only then are the editor-session IDs offered in the `bootReport`. Boot ends by writing `lastIntegrityCheckAt` and continuing the write queue from the loaded revision (so its gap guard is armed). A `revision_gap` (§3) is recovered with `replaceAll`: the user-visible "save everything now" (the button is Phase 5).

`OpenResult` for a loaded database: `mode` (`read_write`, or `read_only` with `readOnlyReason` `other_tab_is_writer` / `newer_schema` / `integrity_failure` / `migration_failed` and a `detail`), `state` (null when nothing is stored or it could not be interpreted), `revision`, `storedSchemaVersion` (as found on disk, before any migration), `quarantinedCount` and the `bootReport` (migration step reports, findings, `assetIdsWithoutBlob`, `crashSuspected`, `editorSessionIds`, `uiState`, `uiStateReset`, `newlyQuarantined`, `singleTab`).

Cold boot budget: < 2.5 s at 2k species / 5k reactions (PERFORMANCE_ARCHITECTURE.md §2).

## 5. Assets

Ingest: size cap (20 MB) → magic-byte sniffing must agree with the declared media type → SHA-256 via `crypto.subtle` → de-duplicate by hash → store Blob in `assetBlobs` and the `asset` record in `records` in one transaction: the blob is passed to `writeChanges(changes, next, blobs)` with the ChangeSet that creates (or, for an import that replaces an asset with different bytes, updates) the record (there is no separate blob write, so a crash can leave neither an orphan blob nor a record without bytes). Blobs of deleted asset records are kept, because undo needs them; sweeping orphan blobs is a Phase 9 Diagnostics action, reported and confirmed by the user, never automatic. Display uses object URLs created and revoked by a component-lifetime hook; SVG assets are displayed only through `<img>` (SECURITY.md §2). Boot integrity reports asset records whose blob is missing (AST-002).

## 6. Import (#15)

```
file ─► size caps ─► compute worker: safe JSON parse (depth ≤ 64, strings ≤ 1 MB, unsafe keys renamed)
     ─► detect format: orn.dataset | orn.package (zip) | legacy v6/v4 export
     ─► legacy? convert (MIGRATION.md §4) ─► schema migrations to current version
     ─► per-record L1; failures → quarantine list (not the whole file)      ◄── step 3.6 stops here
     ─► ID conflict analysis against current state                          ◄── step 3.7
     ─► L2/L3 on the MERGED replica (never on live state)
     ─► ImportPreview: counts, conflicts, quarantined, findings, decisions, legacy report
user confirms (or cancels: nothing changed)
     ─► pre_import snapshot ─► ONE replaceState (or merge commit) ─► history cleared ─► batch report stored
```

Conflict resolutions per ID: `identical_skip` (same content, deep-equal after canonical ordering), `keep_current`, `replace`, `import_as_copy` (new IDs via the reference engine's `remap`, references inside the imported set rewired). Default is the non-destructive choice. Modes: `replace_all` (restore a backup) and `merge`. If the merged result would contain L1–L3 ERRORs, confirmation is disabled until the user excludes the offending records or picks another resolution.

Undo history is cleared after an import because patches cannot span a wholesale replacement; the pre-import snapshot is the undo, offered prominently ("Undo import" restores it).

**Step 3.6 (`src/io/import-source.ts` and its siblings)** builds everything up to and including per-record L1: caps (byte size before the Blob is read; an iterative, string/escape-aware pre-scan of the text enforces depth ≤ 64 and string length ≤ 1,000,000 characters BEFORE `JSON.parse`, so a hostile file is rejected without ever building a parse tree; record count ≤ 200,000 checked on the envelope); the safe parser (`JSON.parse`, then an iterative rename of `__proto__`/`constructor`/`prototype` at any depth); format detection (`orn.dataset` / `orn.package` / `legacy_v6` / `legacy_v4`, MIGRATION.md §4.1 — container detection, zip vs plain JSON text, is a byte-level magic-number sniff one level up); `.ornpkg` unpack (fflate, bounded: each entry's declared size is checked against its own cap before fflate even attempts to inflate it, and fflate's own `unzipSync` additionally pre-allocates the OUTPUT buffer at that declared size, so a lying zip cannot inflate past it either; unsafe/duplicate/unexpected entry names rejected and reported; `manifest.json` required; `dataset.json`'s SHA-256 must match the manifest or the whole import is refused; an asset file's SHA-256 or magic bytes not matching is reported and that one asset's bytes are left out, never the whole import; more than 65,535 entries refuses the package before anything is inflated; an `.orn.json`'s `embeddedAssets` are hashed like package files, and every unusable entry — malformed base64, oversized, no matching record, wrong hash — is a `RejectedAsset` with a reason, never skipped silently); the migration hook (an injected `MigrationRunner`; a newer schema version is refused with an explanation, ADV-041 file part; an older one is migrated on the tolerant envelope before L1); per-record L1 with quarantine (below; a record listed under another envelope group than its own `kind` still imports under its own kind and is reported in `kindMismatches`). The legacy formats are detected but not yet converted (MIGRATION.md §4, steps 3.8-3.11); the result is a plain-data value step 3.7 consumes — nothing is written anywhere by this step.

**Step 3.7 (`src/io/import-conflicts.ts`, `import-request.ts`, `import-merge.ts`, `import-validate.ts`, `import-preview.ts`, `import-apply.ts`, `import-session.ts`, ports in `import-ports.ts`)** builds the rest. Three pure stages feed one plan: (1) *conflict analysis* — each incoming record against the live record of the same ID; `identical` is canonical deep equality of deterministic serialisation (`canonical-json.ts`: keys sorted, arrays in order, never by name or ID); a record that repeats an ID earlier in the SAME file keeps its first occurrence and the repeat is listed in `preview.quarantined` with a reason. (2) *merged replica* — `merge` starts from the live records and adds new ones, replaces (`replace`), leaves the live one (`keep_current`, `identical_skip`) or adds a copy under new IDs (`import_as_copy`); `replace_all` is the incoming records alone with the file's own dataset meta (a missing or invalid meta is refused as `INVALID_META`, and `replace_all` takes no per-record resolutions). `import_as_copy` gives the record AND its nested IDs new IDs from the injected `IdFactory` (kept across revisions of one plan), then rewires every written record's references (`ReferenceEngine.remap`) and rich-text `[[id]]` links (`rewriteRecordRichTextLinks`, registry-driven over `RICH_TEXT_PATHS`; only links the parser itself sees are rewritten; links to IDs outside the copied set are untouched); the preview counts the rewritten links. (3) *validation* — L2/L3 on the merged replica only (`validateAll` over indexes built for the replica; live state and the live finding store are never touched). The preview lists at most 2,000 findings, errors first, and `findingSummary` counts all of them. **Defaults are non-destructive:** `merge`, identical → `identical_skip`, different → `keep_current`, nothing excluded. `canConfirm` is false while the merged result has any L1–L3 ERROR (`blockers` says how many); the user excludes records (`ImportPlanRequest.excluded`) or changes a resolution and asks for a new preview. ADV-031 measured: a wrong-prefix and a wrong-kind reference are both caught at L1 (the record is quarantined); the records that referenced it then show as dangling references on the merged replica (ADV-030).

*Pending batch (Q12).* `createImportSession` keeps at most one: a successful `preview` or `revise` (the FULL desired request, not a delta; a new `batchId`) replaces it, `cancel` discards it, apply consumes it. `apply(batchId, plan)` is refused as a value when the batch is unknown (`UNKNOWN_BATCH`), when the plan's mode/conflicts/excluded/copy map differ from the previewed one (`PLAN_MISMATCH`), when the live revision is not the one the preview was built on, checked before AND after the snapshot (`STALE_REVISION`, "data changed since the preview; run it again"), when the merged result cannot be confirmed (`BLOCKED`, before any snapshot) or the tab is read-only. **Apply:** `pre_import` snapshot (`SnapshotPort`) → ONE `replaceState(merged, 'import')` in both modes (so history is cleared) → batch report and the import's quarantine rows (`ImportBatchSink`, rows carry the `importBatchId`); a store refusal deletes the snapshot again and changes nothing; a report that cannot be stored is reported (`reportSaved: false`), never thrown. The applied state is the merged replica the preview validated. **"Undo import"** is restoring the `pre_import` snapshot (`restoreSnapshot`, §9). Ports (`ImportStorePort`, `SnapshotPort`, `ImportBatchSink`, `AssetStagePort`) are declared in io in the shape the persistence adapter already has, so `adapter.createSnapshot`/`deleteSnapshot`/`saveImportBatch`/`addQuarantine` satisfy them structurally; io never imports persistence.

*Asset bytes (Q1).* Verified bytes of the asset records the plan writes are handed to `AssetStagePort.stage` just before `replaceState`, which notifies the write queue synchronously; the wiring's `blobsFor` (`attachWriteQueue` options) reads them, so bytes and records reach IndexedDB in the SAME transaction. A blob may ride with an asset record the ChangeSet created OR updated (replaced with different bytes). The preview says how many payloads will be stored, how many are not (record skipped/kept), which asset IDs have their existing bytes overwritten, and how many written asset records have no verified bytes in the file (AST-002 later). Snapshots do not hold asset bytes, so "Undo import" cannot bring back bytes an import overwrote (only possible when an asset ID is replaced by one with a different SHA-256, which the preview lists).

## 7. Tolerant envelope and quarantine

Importers parse a tolerant envelope first (format, `records` as arrays of unknown) so one bad record never rejects a whole file. **`schemaVersion` is checked as any number, not `DatasetEnvelopeSchema`'s `min(1)`** (step 3.6, the same reading step 3.3's review gave `decodeSnapshot`: "it accepts any numeric schemaVersion — the runner decides usability — so a file claiming version 0 or -5 reports the migration runner's own `INVALID_VERSION` explanation, not a generic envelope rejection). Records failing L1 go to `quarantine` with the raw value and the issues. For **import** quarantine (the source file still exists) the raw value is kept whole up to 64 Ki characters of its JSON text (the cap is in characters, like the other text limits); a longer one is kept as its first 64 Ki characters and `rawTruncated.originalChars` says how long it was. **Boot** rows are never capped: boot moves the row (§4), so the quarantine row holds the only copy, whole and exactly as stored (a value that is not plain JSON, such as a Date or NaN, is kept as it is and the issues say so); `rawTruncated` is never set on them. The 64 Ki cap is for display only there. `import` rows carry the `importBatchId` (added when step 3.7 stores the batch); rows are added in the write queue's order and a row whose ID exists is kept as it is. Keys `__proto__`, `constructor` and `prototype` are renamed during parsing (`__unsafe_key__…`) and reported (`path` + the original key), preventing prototype pollution without silent loss — proved by a test that `Object.prototype` is unchanged even after the sanitised value is spread or `Object.assign`-merged.

## 8. Export

- **`.orn.json`** — one `DatasetDocument`. Records sorted by ID within each kind, object keys in schema order, 2-space indentation, LF, trailing newline. Export → import → export is byte-identical (property test P-02, full pipeline through the real importer since step 3.7: `tests/property/import-export-roundtrip.test.ts`; plus "save → load → export equals export of the original"). `assets: 'embed'` adds `embeddedAssets` (base64); `'none'`/`'package'` write no bytes into the single file.
- **`.ornpkg`** — zip (fflate, `src/io/export-package.ts`): `manifest.json` (`{ format: 'orn.package', schemaVersion, files: [{ path, sha256 }] }`, one entry for `dataset.json` and one per included asset file), `dataset.json`, `assets/<sha256>.<ext>` (written when `assets` is `'embed'` or `'package'`). Determinism (INV-19): every zip entry carries one FIXED modification time (the ZIP/MS-DOS epoch, 1980-01-01 — not the current time, and not Unix's 1970 epoch, which the DOS date range rejects) and a fixed entry order (manifest, dataset, then assets sorted by sha256), so the same state and clock give byte-identical bytes on every run, both formats.
- **Scopes** (`src/io/export-scope.ts`; step 3.5 REVIEW REQUIRED 1, approved in the step 3.5 review, 2026-09-29 — this section was ambiguous, so the reading chosen, and now confirmed, is the one that makes every named scope's output free of dangling references, since `ExportOptions` has no flag to gate it per scope; a "curriculum without its mapped chemistry" option is FUTURE, not built — nothing needs it): `full` (everything); `chemistry` (layers 1–2 whole, plus every asset that attaches to a record in it — a REVERSE pass, since an asset forward-references what it attaches to, `asset.attachedTo[].ref`, never the other way; a plain forward closure from layers 1–2 adds nothing new, INV-29); `curriculum` (layers 1+3 whole, plus the forward closure of whatever they reference — chiefly the chemistry record a `topic_mapping`/`exam_relevance` maps, and in turn whatever THAT record needs to resolve); `presentation` (layer 5 whole, plus the forward closure of whatever it references — the chemistry a hub/scheme points at, the asset a scheme prefers, the topics/exam a view preset filters by); `subset` (exactly the given records, plus the forward closure when `includeDependencies`; without it, references leaving the subset are reported in `ExportResult.missingReferences`, never silently dropped or silently kept — the only scope where this list can be non-empty). The closure itself is generic (`src/core/references` `ReferenceEngine.extract`, REFERENCE_SPECS), never a per-kind or per-field special case.
- **Asset bytes**: `AssetBytesProvider(assetId, sha256) => Promise<Uint8Array | undefined>` (`src/io/contracts.ts`) is passed BESIDE `ExportOptions`, never inside them (options stay structured-clone-safe); `undefined` is reported in `ExportResult.missingAssets`, never thrown and never a reason to fail the rest of the export.
- **`ExportResult`**: `{ bytes, counts, missingAssets, missingReferences }` — nothing about a gap is silent (CLAUDE.md §1.5). Building either format takes an optional `TaskOptions { signal?, onProgress? }`; a signal aborted mid-export returns a value with no partial bytes, and progress is reported once per asset written/embedded plus once for the final serialise/zip step.
- **Images**: SVG and PNG of the current view are produced from the same Scene as the screen (UI_ARCHITECTURE.md §6); PNG via canvas rasterisation of that SVG.

## 9. Snapshots

- Mandatory before import, migration and restore (reasons `pre_import`, `pre_migration`, `pre_restore`; never pruned). Manual snapshots are kept until the user deletes them. Periodic snapshots are taken during editing, after 30 minutes of activity or 200 revisions, whichever comes first (activity starts with the first ChangeSet after the previous snapshot; injected clock; `createPeriodicPolicy`, `startPeriodicSnapshots`). Creating a periodic snapshot prunes all but the newest 5 periodic ones in the same transaction, and reports the pruned IDs.
- Format: a `full` DatasetDocument as deterministic JSON text (the strict schema, so a state that does not serialise is refused, never stored), compressed with fflate (zlib: no timestamp, so identical states give identical bytes). Building and decoding are pure functions (`buildSnapshot`, `decodeSnapshot`) hosted by the compute worker from Phase 4. Decoding is bounded (inflated size cap 200 MB) and every kind of damage is a value: `readSnapshot` returns `{ ok: true, summary, doc }` with the TOLERANT `MigratableDocument` (an older snapshot must be migrated before it parses strictly) or `{ ok: false, code: 'NOT_FOUND' | 'CORRUPT', message }`.
- Creating and deleting run in the write queue's order (§3). Snapshot bytes are never part of a ChangeSet transaction.
- Restore (`restoreSnapshot`): read → migrate (the injected `MigrationRunner`, if the snapshot is older) → strict L1 parse → `pre_restore` snapshot of the live state (taken again, at most 3 times, if the live data changed while it was written) → `replaceState(…, 'restore')` (validated like a commit, history cleared) . The result is a value: `ok: true` with the `pre_restore` summary (restoring it is "undo restore") and the migration step reports, or `ok: false` with `READ_ONLY`, `NOT_FOUND`, `CORRUPT`, `MIGRATION_FAILED` (the runner's error attached), `INVALID` (bounded L1 issues), `REJECTED` (the store's L1–L3 refusal; the `pre_restore` snapshot made for it is removed again) or `SNAPSHOT_FAILED`. A failed restore changes nothing: not the live state, not its history, not the stored snapshots. The restored state reaches IndexedDB like any ChangeSet (the store's `replace` ChangeSet through the write queue); the caller may `flush()` to wait for it.

## 10. Multiple tabs

The tab holding the Web Lock `orn-writer` is the only writer (INV-28, ADR-005, ADR-033). Both browser objects are **injected** from outside `src/persistence` (`createWebLocksWriterLock(navigator.locks)`, `createBroadcastChangeChannel((name) => new BroadcastChannel(name))`), never read as globals. Tests use in-memory fakes (`src/test-support/tab-fakes.ts`) and, for the main scenario and the two ports, Node 24's real `navigator.locks` and `BroadcastChannel`.

- **Lock.** `WriterLock.acquire()` is one non-blocking attempt: `'acquired'`, `'held_elsewhere'` or `'unsupported'` (no Web Locks, or a context that refuses them). `'unsupported'`: nothing can keep a second tab out, so the tab runs as the writer and boot reports `bootReport.singleTab` (the app shows a single-tab warning). `whenAcquired()` resolves when a tab that got `'held_elsewhere'` is granted the lock (the writer closed; a closed or crashed tab loses its lock). `release()` resolves once the lock is really free.
- **Writer → followers.** After each persisted transaction the writer posts `ChangeMessage { fromRevision, revision, changedIds }`: `fromRevision` is the revision the database was at before the transaction (a coalesced transaction names the whole span), `changedIds` the IDs of the records it created, updated or deleted, or `'all'` when there are more than 2,000 of them and after `replaceAll` (migration, "save everything now"). Nothing is posted before the transaction is durable or when it fails. A channel that throws is reported (`channel_error`) and never fails the write.
- **Follower.** Boot without the lock loads the state and writes nothing (§4 step 2). The tab shows "Open in another tab — read-only" and handles messages strictly one at a time, in order (a backlog beyond 100 becomes one full reload). A message is validated and bounded first (another tab is not trusted); a malformed one, or one whose `revision` is not newer than the follower's, is ignored and reported. `'all'`, no state yet, or `fromRevision` different from the follower's revision → **full reload**. Otherwise the follower re-reads the changed rows, the revision and the dataset meta in ONE read transaction; if the database is no longer at `revision`, or a row fails L1 (reported; a follower never writes, so it never quarantines), it reloads fully; else it calls `store.applyRemote`. A full reload leaves rows that fail L1 out of the state and reports them. Stored data of another schema version loads nothing (only the writer migrates; the message its migration posts brings the data).
- **Promotion.** `whenAcquired` resolves → the write queue becomes writable and boot runs again as the writer (§4: migration, quarantine move, markers, crash check, so the old writer's unsaved drafts are offered if it crashed) → `store.reload` from that result → only then does the tab become writable, and only then is a write queue attached to its store (`attachWriteQueue`). Promotion is the only path that makes a read-only tab writable. If that boot refuses (newer schema, failed migration, damaged meta) the tab stays read-only and says why (`promotion_failed`).
- **INV-28 guards (ADR-033).** `applyRemote` and `reload` exist only for a read-only store and are refused as a value (`NOT_FOLLOWER`) on a writable one; a follower has no write queue attached (`attachWriteQueue` refuses a read-only store as a value); a ChangeSet with `cause: 'remote'` is never written, whatever the wiring (a second guard, not the main one). The mirror applies the writer's durable state without an ERROR gate: errors become findings, visibly.

## 11. Quota and durability

`navigator.storage.persist()` is requested after the first edit. Diagnostics shows usage and quota. `derivedCache` keeps itself under a 100 MB soft cap by evicting its least recently used rows when a row is put. On a quota error: evict `derivedCache` (the least recently used half of its rows per round, retrying the write at once after each round, no timer) → **stage 2:** `SaveStatus.failed` carries `deletablePeriodicSnapshotIds`, the periodic snapshots the user may delete to make room, oldest first (mandatory and manual snapshots are never offered; the field is absent when there are none; there is no UI before Phase 5, only the status). Deleting one refreshes the list but does not retry the write: a new ChangeSet or `flush()` does → otherwise `SaveStatus.failed` with "Export now" (pending ChangeSets kept, memory untouched). A cache write that fails is a value (`DerivedPutResult`), never a SaveStatus problem, and every eviction is reported to the diagnostics sink.

## 12. Failure modes (#22)

| Failure | Response |
|---|---|
| IndexedDB unavailable (private mode, blocked) | Session-only mode with a persistent banner; export available; nothing pretends to be saved |
| Write transaction fails | Retry with backoff → failed status + banner; memory kept; export offered |
| Quota exceeded | §11 sequence |
| Corrupt record at boot | Quarantined with issues; rest loads; Diagnostics lists it with export/repair options |
| Migration throws | Automatic restore of the pre-migration snapshot; open read-only; error report exportable |
| Newer schema on disk | Read-only mode with explanation |
| Worker crash | Restart worker, reload its replica from the current state, retry the request once, then surface an error |
| RDKit fails to load | L4 checks and depictions unavailable (clear notice); everything else works; names/formulas shown instead of structures |
| ELK fails or exceeds 2 s | Fallback layered layout; notice in Diagnostics |
| Render error | Error boundary per panel with "Reload panel"; canonical state unaffected |
| Import error at any stage | Nothing changed (INV-21); preview shows the error |
| Tab or browser crash | Editor sessions are saved every 2 s while dirty; offered for restore on next boot |

## 13. UI state

Stored in `uiState` with tolerant schemas (invalid entries are reset, never block boot): selection, per-view viewport, expansion state, open panels and widths, inspector disclosure level, active exam and exam version, last view, recent searches. It is never exported with the dataset unless the user explicitly exports a "workspace" (FUTURE).
