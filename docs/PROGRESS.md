**Delivered** (`src/core/text/`, contracts unchanged)

- `richtext.ts`: `parseRichText` (paragraphs, bullets, `*em*`, `**strong**`, `_{sub}`, `^{sup}`, `[[id]]`/`[[id|label]]` links) and `richTextLinks` (distinct links, first-appearance order, for REF-008). Total: malformed markup is kept as literal text; no character is dropped.

- Invariants/ADV touched: INV-24 (fold never stored, parsing never alters data), ADV-022 (duplicate-name folding basis), ADV-033 (markup inert), REF-008 (link extraction).

**Decisions**
- Dash rule (refines SEARCH.md §2 item 4, which is otherwise self-contradictory for `Br⁻ → br-`): a dash directly after a letter/digit and not before one is a charge sign and is kept as `-`; every other dash variant becomes a space. Side effect: `10⁻³` folds to `10 3`. Docs updated in the same commit.
- Only U+0300–U+036F are stripped as diacritics so Devanagari and other scripts survive.
- Emphasis delimiters must touch non-space text (`2 * 3 * 4` stays literal). Sub/sup/link bodies are single-line; sub/sup non-empty; link IDs must be valid record IDs, an empty label after `|` is malformed, and a missing label defaults to the target ID.
- Bounds: inline nesting depth ≤ 4 (deeper content literal); closer searches share a work budget of 1,000 + 50 × length, after which openers are literal. Adversarial inputs (16k unclosed openers) parse in well under a second.

**Open items**
- Renderers (step 5.x) resolve a link label that equals its target ID to the record's display name; the parser stays chemistry-free.

### Step 1.5 — `core/dataset`: document ↔ state, serialisation, ID factory, ChangeSets (2026-09-26)

**Delivered** (`src/core/dataset/`)
- `ids.ts`: `createIdFactory(clock, rng)` → `{ now(), newId(prefix) }` (structurally a `CommandContext`). `<prefix>_<lowercase ULID>`: 10 time + 16 random Crockford-base32 characters. Monotonic per factory (same millisecond increments the random part; a clock stepping backwards keeps the last time), so IDs sort in creation order. Overflow, a malformed prefix, an out-of-range clock or an RNG value outside [0, 1) throw `RangeError` (programmer errors).
- `document.ts`: `documentToState` (deep-frozen state; duplicate IDs across all kinds returned as a value, never merged; embedded asset bytes returned beside the state) and `stateToDocument` (records sorted by ID in code-unit order, every kind present, `embeddedAssets` only when supplied and non-empty).
- `serialize.ts`: `serializeDocument` / `deserializeDocument`. Key order is schema order because the document is re-parsed through the strict schema; 2-space indent, LF, trailing newline. Invalid input yields `{ ok: false, issues }` with paths; nothing is repaired.
- `changeset.ts`: `assembleChangeSet` classifies created/updated/deleted from Immer patches in O(patches) (create-then-delete collapses to nothing, delete-then-recreate is `updated`, lists sorted by kind order then ID). Patches too coarse to name a record (whole table or whole state) and `cause: 'replace'` fall back to `diffStates`, which skips unchanged tables and records by identity.
- Contracts: `Clock`, `RandomSource`, `IdFactory` added to `dataset/contracts.ts` (additive types only; `ChangeSet` unchanged, no schema change, no version bump).
- Tests (51): `ids.test.ts` (12), `document.test.ts` (23, both fixtures), `changeset.test.ts` (16).
- Invariants touched: INV-01 (duplicate reporting), INV-03 (ULID IDs, injected RNG/clock), INV-19 / P-02 in memory (both fixtures serialise byte-identically to the committed files, through state, from shuffled keys and reversed insertion order), INV-23 (embedded assets not dropped), INV-10 (unknown keys refused), INV-27 (patch/inverse round trip, undo swaps created/deleted), ADV-020 (ID uniqueness input for regenerated nested IDs).

**Decisions**
- Embedded asset bytes are not canonical state, so `documentToState` returns them next to the state and `stateToDocument` takes them in its options. Callers (io, step 3.x) own them.
- Free-form JSON (`provenance.legacy.unmapped`) keeps its own key order; it is user data and the schema cannot mark it. Round trips stay byte-identical because JSON preserves order.
- `serializeDocument` validates with the full strict schema, so exporting an invalid state is refused with issues rather than written.
- `ChangeSet` `created/updated/deleted` are net effects; intermediate states inside one command are not visible.

**Open items**
- Immer patches require `enablePatches()`. Nothing in `src/core` calls it yet; the store (step 1.9) must, once at module load. `changeset.test.ts` calls it itself.
- `deserializeDocument` is strict and single-shot. The tolerant envelope, quarantine and prototype-key renaming (PERSISTENCE.md §7) belong to the importer (step 3.x).

### Step 1.6 — `core/indexes` part 1: reverse references, folded names, hierarchy ancestry (2026-09-26)

**Delivered** (`src/core/indexes/`)
- `engine.ts`: `coreIndexEngine` (`build`, `apply`) implementing the new `CoreIndexEngine`/`CoreIndexes` contract: `get`, `referrersOf` (record and nested IDs, sorted by owner ID then path, carrying the registry delete policy), `byFoldedName` (per kind, sorted by ID), `ancestorsOf` / `descendantsOf` / `classAncestors`. Every record contributes only from its own content, so `apply` retracts and re-adds just the created/updated/deleted records (O(changed × references)) and equals a rebuild (INV-18).
- `hierarchy.ts`: parent-field table (class, concept, named_reaction `parentIds`; topic `parentId`), cycle-safe iterative breadth-first closure. Descendants come from the reverse-reference index, so no separate children map exists to keep in sync.
- `names.ts`: structural folded-name extraction (`name`, `names.*` except `qualifier`, `aliases`) through `core/text` `fold`.
- `src/test-support/state-fixture.ts`: fixture states and a `commit` helper yielding (state, ChangeSet) as the store will.
- Tests (38): `engine.test.ts` (12: reverse references against an independent oracle over the maximal fixture, ordering, `get`, folded names), `hierarchy.test.ts` (14: table checked against the registry, chain/diamond/cycle/self-parent/dangling, all four hierarchies in the maximal fixture, 5,000-deep chain), `incremental.test.ts` (12: scenarios incl. delete/recreate, undo, replace and revision gap, stale handle, snapshot stability, and four seeded 100-edit random walks compared with a rebuild after every step).
- Invariants touched: INV-11 (nothing stored), INV-18 (apply ≡ build), INV-01 (nested IDs are reverse-index keys), ADV-022 input (duplicate folded names are all returned).

**Decisions**
- In-place update with stale-handle guard: `apply` mutates the shared index data and returns the handle for the new revision; the previous handle then throws on use (a loud programmer error rather than an O(dataset) copy per commit). Arrays already returned stay valid snapshots (buckets are replaced, never mutated). A `replace` ChangeSet or a revision gap rebuilds from `next` instead, leaving the previous handle usable.
- `byFoldedName` covers every name of a record (canonical, display, IUPAC, common, aliases); the caller supplies the folded query. Rules that need canonical-only matching (SPC-001, step 1.8) filter on the record.
- Ancestor walks skip parents that have no record (dangling parents are L2 findings); cycles are walked once and never list the start.
- Hierarchy walks are computed on demand, not cached: work is bounded by the reachable records. Caching is a Phase 2 concern if profiling asks for it.

**Open items**
- Part 2 (step 2.1) adds the remaining `ReadonlyIndexes` methods (participations, productions, by reagent/…, topics of a record, relationships, caveats, anchors, display) and a combined engine; the property test P-07 over random commands is step 1.11.

**Delivered** (`src/core/validation/`, plus `src/core/schema/rich-text.ts`)

- `FoundRoute.score` is populated (`steps.length*1000 + worstSelectivityRank*100 + inferredCount*10 + draftCount`) but documented as informational: the ranking rule's final tie-break (reaction-ID sequence) is lexicographic on strings, which a single number cannot encode losslessly against the earlier criteria, so the authoritative order is the array `rankRoutes` returns, not a derived sort of `score`.
- No worker wiring yet (Phase 4): `searchRoutes` is a pure, synchronous core function; `workers/rpc/contracts.ts`'s `findRoutes(params: RouteQuery, ctx): Promise<RouteSearchResult>` will wrap it with cancellation/progress plumbing when the compute worker is built.

**Commit 2 — field-aware `validateTouched` scope: report and decision.**

*How `scopeOf`/`validateTouched` use `watches`/`peers` today* (`src/core/validation/validator.ts`):
`scopeOf` adds, for every touched record (in both its new and previous version): (a) **every** referrer
from `indexes.referrersOf`, unconditionally; (b) every referent the record's own references point at; (c)
for rules that declare `.peers()`, whose `kinds` or `watches` include the record's kind, whatever
`.peers(record, ctx)` returns. `validateTouched` then runs **every** L2/L3 rule applicable to each scope
member's kind (`findingsOf`), regardless of *why* that member is in scope. `watches` is a record-*kind*
list ("besides `kinds`, which other kinds' changes should make me consider `.peers()`"); `.peers()` is
rule-specific but still returns whole records, not fields. **Neither carries any field-level information at
all** — there is no way, from what a rule declares today, to ask "did the field this rule actually reads
change on the touched record?" The closest existing lever is `ValidationRule.scope` (`'record' |
'neighbourhood' | 'global'`): a `'record'`-scoped rule's verdict on a *referrer* R can never change from R
merely being a referrer of some other touched record — R's own content didn't change. In principle this
lets some rule executions be skipped for context-only scope members. In practice it does **not** save
anything safely: `commitFindings`/`FindingStore.replaceForSubjects` does a wholesale replace of a subject's
findings at a level — if `validateTouched` simply omits a `'record'`-scoped rule's finding for R (rather
than recomputing it), the store would wrongly clear a still-valid finding, since nothing carries the old
value forward without a `FindingStore` reference in `validateTouched`'s signature (which would itself be a
contract change). And since `'record'`-scoped rules by definition read only the record itself (cheap,
local checks — kind/prefix match, self-reference, local-ID resolution), *recomputing* them is not the
expensive part of a hub-record commit; the expense is the sheer count of referrers run through the whole
rule pipeline (`runRules`, finding-ID hashing, sorting) regardless of which specific rules fire.
**Conclusion: no safe, correct narrowing of `validateTouched`'s scope is possible with today's metadata
(kind-level `watches`, record-level `peers`, three-valued `scope`) without adding field-level dependency
information to `ValidationRule` — a contract change.** Per this step's instructions, the contract is left
unchanged. Instead: PERFORMANCE_ARCHITECTURE.md §2 gains a new row, "Commit on a record with ≥ 500
referrers: < 50 ms p95" (not a new "Commit" row, a *different* operation with its own, looser budget — a
hub-record commit is a qualitatively different case, not a regression of the plain one). A regression
benchmark already existed for this shape (`commit.bench.ts`'s `validateTouched` benches on both the
ADV-012 literal hub and the design-tier "like water" hub, step 2.9); `tests/perf/budgets.mjs` now maps both
to the new row instead of the plain 16 ms Commit budget.
*Doubled `scopeOf` call*: unaffected by this step (no scoping change was made to remove it) — recorded as
a **Phase 9 candidate** (PROJECT_STATE.json open items), not attempted here, per this step's own framing.

### Step 2.12 — Field-aware validation scope (2026-09-28)

**Commit 1 — `phase-2.12: field-aware validation scope (ADR-031)`.** Reviewer decision: implement

touched records and their reverse-index dependents") through an additive `ValidationRule` amendment; a rule that
does not declare it keeps today's behaviour. Full amendment under "Amendments" below, and ADR-031.

- **Contract** (`src/core/validation/contracts.ts`): `referencedReads?: ReferencedReads` - what a rule's `check`
  reads of the records its subject refers to. The shape sits beside `watches`/`peers`: those say which *other*
  records a change reaches, at kind/record level; this says which *fields* of the records a rule refers to it
  reads, the missing half. Keys are a referenced kind or `'*'`; values are top-level field names; `[]` is "only
  whether it exists", an absent kind is "not read".
- **Scoping** (`src/core/validation/scoping.ts`, used by `validator.ts`): `changeOf` diffs the touched record's
  new and previous versions by top-level field, by reference (exact under structural sharing; a created or

  per touched record, so a 1,000-referrer hub costs one rule scan, not 1,000. A referrer is kept if any L2/L3
  rule of its kind reads a changed field. Referent expansion and `peers`/`watches` are untouched (RXN-018 and
  AST-001 read their own referrers and depend on the referent expansion). The referrers lookup now runs once
  per touched record instead of once per version (same ID).

**Decisions**
- *Coalescing and INV-20.* The plan says "one transaction per ChangeSet … coalescing per record". Implemented as: every
  transaction is atomic and lands the database on a real committed revision; ChangeSets that wait together (same tick,
  or while a write or backoff is running) share ONE transaction that ends at the newest revision. An idle queue writes
  each ChangeSet on its own (the tests count the transactions). If the reviewer wants strictly one transaction per
  ChangeSet even for queued ones, that is a change to `resolveWrites`/`mergeBatches` only.
- *A failed batch is kept, never skipped.* Writing a later ChangeSet while an earlier one failed would leave a database
  state memory never had. After `failed`, the next `writeChanges` or `flush()` starts a fresh retry cycle over
  everything pending. `writeChanges` resolves when its write cycle ends (durable or `failed`); callers read `getStatus()`.
- *Revision-gap guard.* A ChangeSet that does not follow the previous revision is refused (exception + status `failed`):
  a ChangeSet the queue never saw would leave its record changes out of the database for good. The first ChangeSet
  establishes the revision unless `initialRevision` is given (boot will).
- *One microtask of grace* before a write cycle starts, so a command loop in one tick makes one transaction.
- *Quota* (ADV-040 stage 1): evict the least recently used HALF of the derivedCache rows, retry at once (no timer), repeat
  until nothing is left to free, then `failed`. Snapshot deletion (stage 2) is 3.2. A cache write that fails is a value
  (`DerivedPutResult`), never SaveStatus.
- *`DexieAdapter` is a `Pick` of `PersistenceAdapter`* plus `flush` and `readCommitted`. Not yet implemented, each in the
  step that needs it: `open` (3.3), `replaceAll` (3.3, migration), snapshots (3.2/3.3), editor sessions and uiState (3.3
  reads them at boot), `storageEstimate` and `requestPersistentStorage` (Phase 5/9 wiring). The clean-shutdown setters write
  directly; the caller must check `getStatus()` first (that is what the pending-writes query is for).
- *Read-only* is a constructor flag for now (status `read_only`, writes refused); promotion to writable is 3.4.
- `test:coverage` now also covers `src/persistence` with an 80% lines threshold (`vitest.config.ts`, package script).

**Decisions**
- *Message semantics.* `fromRevision` is the revision the database was at before the transaction, tracked by the adapter (boot's `continueFrom`, every persisted transaction, `replaceAll`); with no boot it is `revision − count`. A coalesced transaction is ONE message over the whole span. Nothing is posted before the transaction is durable or when it fails; a failed cycle's retry posts once with the same span; a write that ends `failed` posts nothing and the next success names the whole gap. A channel that throws is a `channel_error` event, never a failed write.
- *`'all'`.* `replaceAll` (boot migration, "save everything now") rewrites everything, so a list of IDs would be wrong for a follower at the old revision (recovery re-saves at a revision the follower may not have). Also used beyond 2,000 changed IDs, so a message and the follower's read stay bounded. A follower reloads fully on `'all'` (unless the message is older than its revision).
- *Follower rules.* Strictly in order, one at a time; a message whose `revision` is not newer is ignored (the follower may already have read past it); `fromRevision` ≠ current → full reload; the read is ONE transaction over the rows, `meta.revision`, `meta.schemaVersion` and `datasetMeta`; a database at another revision or schema version → full reload (never a wrong apply); a row failing L1 or a meta failing its schema → reported, full reload; `applyRemote` `STALE_REVISION` / `INTERNAL` → full reload; `NOT_FOLLOWER` (a misconfigured store) → `apply_refused`, nothing applied. A full reload leaves rows that fail L1 out of the state and reports them (no loop: it happens once). Backlog beyond 100 messages → one full reload. Malformed messages are ignored and reported (a junk flood cannot cause reloads); the next real message heals a follower that missed one.
- *Promotion.* `whenAcquired` resolves → the queue becomes writable and boot runs again as the writer (migration if needed, quarantine MOVE, markers, crash check: the old writer's editor sessions are offered when it did not shut down cleanly) → the store reloads from that result while still read-only → the tab becomes writable → the app attaches the write queue. A refused boot (newer schema, failed migration, damaged meta) gives the lock back and leaves the tab read-only and following, with `promotion_failed`. A store handed a state of nothing, or refusing the state, also fails the promotion (queue read-only again, lock released). Read-only becomes switchable only through promotion (`adapter.promote`).
- *No Web Locks.* `acquire()` answers `'unsupported'` when there is no `LockManager` or `request` throws: the tab runs as the writer, `bootReport.singleTab` is true (also for a fresh database, whose boot result now carries a `bootReport`).
- *A lockless tab that needs a migration* opens read-only with `state: null` (3.3); when the writer's migration posts its `'all'` message the follower loads (a `loaded` event, the app builds the store and `attach`es it).
- *`release()` waits until the lock is really free.* Real Web Locks free the lock a moment after the holder's callback settles; a `release()` that resolved earlier let the same tab's next `acquire()` see `held_elsewhere` (found by the real-`navigator.locks` test).
- *ERROR gate.* None on a mirror (the fit scan's wording): the writer accepted the state and it is durable; errors become findings in the follower's finding store, and `applyRemote`/`reload` return them.
