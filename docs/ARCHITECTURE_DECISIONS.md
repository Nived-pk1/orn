# Architecture Decisions

Package section **#3 Technology Decision & Alternatives**. Each ADR records requirements, the decision, advantages, disadvantages, performance, maintenance, migration implications, why it was chosen and why alternatives were rejected. ADRs are append-only: to change a decision, add a new ADR that supersedes the old one and update CLAUDE.md.

---

### ADR-001 — TypeScript (strict) + React 19 + Vite 7
- **Requirements**: multi-file modular codebase maintainable by AI agents; rich interactive UI; offline static delivery; strong types across a large domain model.
- **Decision**: TypeScript with `strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`; React 19 function components; Vite 7 for dev server, workers and builds.
- **Advantages**: types make the canonical model self-documenting and refactor-safe; React's ecosystem covers accessible primitives, virtualisation and testing; Vite handles ES-module workers and WASM with no custom config.
- **Disadvantages**: React re-render costs must be managed (selectors, imperative viewport); build tooling churn.
- **Performance**: React is used for structure; hot paths (pan/zoom, culling) bypass React; Vite produces code-split ES2022 bundles.
- **Maintenance**: mainstream stack; abundant documentation; agents know it well.
- **Migration implications**: core is framework-free (`src/core` imports only zod and immer), so a future UI rewrite does not touch the domain.
- **Why chosen**: best balance of ecosystem, agent familiarity and performance control.
- **Rejected**: Svelte/SolidJS (smaller ecosystems for accessible primitives and testing, less agent familiarity); Angular (heavy, slower iteration); plain JS (the v6 lesson: no types, one file, fragile).

### ADR-002 — Zod 4 as the canonical schema language
- **Requirements**: one executable source of truth for types and runtime validation; strict unknown-key rejection; branded IDs; discriminated unions; readable by agents.
- **Decision**: Zod 4 (`strictObject`, `discriminatedUnion`, `brand`, `lazy`), no defaults or transforms in canonical schemas; `z.config({ jitless: true })` for CSP. Phase-0 schemas use the Zod 3/4 common subset and were verified with tsc 6.0.3.
- **Advantages**: types inferred from schemas; precise error paths for findings; widely known.
- **Disadvantages**: bundle size larger than Valibot; jitless mode is slower than JIT.
- **Performance**: per-record parsing is cheap (tens of µs); full-dataset parsing happens in workers.
- **Maintenance**: schema files are small and declarative; one file per domain area.
- **Migration implications**: schema changes are versioned (MIGRATION.md §1); old schemas are preserved in migration steps as plain data transforms.
- **Why chosen**: maturity, error quality, agent familiarity.
- **Rejected**: Valibot (smaller, but less familiar and less mature error tooling); ArkType (novel syntax, harder for agents to maintain); TypeBox + Ajv (Ajv compiles with `new Function`, conflicts with CSP; JSON Schema is verbose for this model).

### ADR-003 — Immer-based command store with patches
- **Requirements**: exact undo/redo; change sets for persistence, indexes, search and worker replicas; immutable state for cheap equality.
- **Decision**: all changes are commands executed with Immer `produceWithPatches`; patches and inverse patches form ChangeSets and history entries.
- **Advantages**: one mechanism powers undo, persistence and incremental derivation; structural sharing.
- **Disadvantages**: patch paths couple to state shape (`records.<kind>.<id>`), so the state shape is part of the contract.
- **Performance**: small commits allocate only changed paths; freezing in dev only if profiling shows cost.
- **Maintenance**: command builders are plain functions; the store is small.
- **Migration implications**: history never spans schema versions (cleared on migration/import).
- **Why chosen**: simplest correct way to get exact undo and incremental everything.
- **Rejected**: Redux Toolkit (same Immer core with more ceremony); event sourcing log as primary storage (replay cost, schema-versioned events); CRDTs/Yjs (multi-user sync is FUTURE; unnecessary complexity now).

### ADR-004 — IndexedDB via Dexie 4 with a generic records table
- **Requirements**: offline, durable, transactional, large capacity (tens of MB + images), works in all modern browsers.
- **Decision**: Dexie 4 over IndexedDB; one `records` store keyed by ID with a `kind` index; separate stores for blobs, snapshots, sessions, caches, UI state, quarantine.
- **Advantages**: transactions; large quotas; Blob storage; mature library with good TypeScript types and fake-indexeddb testing.
- **Disadvantages**: IndexedDB quirks (private mode, Safari quotas); no SQL queries (not needed: indexes are in memory).
- **Performance**: bulk reads at boot; one small transaction per commit.
- **Maintenance**: schema evolution lives in Zod migrations; Dexie versions change only when stores change.
- **Migration implications**: a future SQLite-WASM/OPFS backend can implement `PersistenceAdapter` without touching the core.
- **Why chosen**: the only universally available transactional browser store; Dexie removes its sharp edges.
- **Rejected**: localStorage (5 MB, synchronous, no transactions — v6's limit); SQLite-WASM on OPFS (excellent but heavier, cross-browser OPFS sync-access maturity and COOP/COEP needs; revisit at scale); idb-keyval (no transactions over multiple keys).

### ADR-005 — Single writer via Web Locks + BroadcastChannel
- **Requirements**: no lost updates when the app is open in two tabs.
- **Decision**: Web Lock `orn-writer`; other tabs read-only and follow changes via BroadcastChannel; promotion on writer close.
- **Advantages**: simple, correct, no merge logic.
- **Disadvantages**: second tab cannot edit.
- **Performance**: negligible.
- **Maintenance**: small module.
- **Migration implications**: real multi-writer sync (CRDT) remains possible later behind the same store interface.
- **Why chosen**: correctness with minimal complexity for a single-user app.
- **Rejected**: last-write-wins across tabs (silent loss); SharedWorker-hosted store (poor Safari history, harder debugging).

### ADR-006 — Custom SVG renderer + d3-zoom viewport
- **Requirements**: chemistry typography (sub/superscripts), structure depictions, accessible nodes, SVG export identical to screen, 60 fps at 400 nodes, full styling control.
- **Decision**: Scene model → React SVG layers; d3-zoom for gestures writing a single transform imperatively; LOD and culling; a WebGL overview layer is FUTURE.
- **Advantages**: pixel-identical export; ARIA on real elements; precise typographic control; no fighting a library's model of nodes/edges.
- **Disadvantages**: more code to own (hit testing, culling, LOD).
- **Performance**: fine at the render budget; LOD and culling keep it there; very large overviews would need canvas/WebGL (FUTURE).
- **Maintenance**: renderer is isolated in `src/render`; the Scene contract decouples it from graph semantics.
- **Migration implications**: a canvas/WebGL renderer can consume the same Scene.
- **Why chosen**: export parity, accessibility and chemistry typography are requirements, not nice-to-haves.
- **Rejected**: Cytoscape.js (canvas rendering: weak accessibility and typographic control; export differs from DOM); React Flow (DOM nodes per element, heavy at scale, opinionated interaction model); Sigma.js (WebGL, excellent for huge graphs but poor text/typography and a11y).

### ADR-007 — ELK (elkjs) in a worker, with an in-house fallback
- **Requirements**: readable layered layouts of bipartite/hub graphs, deterministic, off the main thread.
- **Decision**: elkjs `layered`, `radial`, `stress` in the layout worker; deterministic inputs; 2 s timeout → fallback longest-path layered layout.
- **Advantages**: best-in-class layered layout with port and spacing control; runs in workers.
- **Disadvantages**: large bundle (lazy-loaded); layout quality tuning required.
- **Performance**: < 300 ms for ≤ 400 nodes; cached by key.
- **Maintenance**: adapter isolated behind `LayoutEngine`.
- **Migration implications**: engine replaceable per algorithm.
- **Why chosen**: quality and determinism.
- **Rejected**: dagre (unmaintained, weaker for hubs); D3-force (non-deterministic, unstable positions between expansions); Graphviz-WASM (strong but heavier and awkward in workers).
- **2026-10-01 (step 4.4 review, follow-up a).** ELK layered runs with `elk.edgeRouting` = `POLYLINE` and `elk.layered.thoroughness` = 3. Reason: measured on the 400-node projections they cut layout time from about 590-820 ms to about 300-370 ms (dense navigator 3,300-3,600 to 1,650-1,700 ms) at an acceptable loss of edge-route smoothness and crossing-minimisation effort; the layout stays deterministic (property tests re-run). Also: the request seed reaches ELK as `1 + seed % 2,147,483,646`, because ELK reads a raw 0 as "seed from the clock" (found by the determinism property). Stress over 40 nodes (`MAX_STRESS_NODES`) is laid out by the layout service with ELK layered and says so in `notes`.
- **2026-10-08 (step 5.5a review, item c).** ELK layered edge routing becomes `ORTHOGONAL` (right angles, no diagonal line through text; the navigator draws at most 120 pairs). Layout edges may carry one label (`elk.edgeLabels.placement` CENTER, `elk.edgeLabels.inline` false, `elk.layered.edgeLabels.centerLabelPlacementStrategy` MEDIAN_LAYER, a stated `elk.spacing.edgeLabel`). The 400-node layered bench is re-run once, alone; a mean over 1,000 ms stops the step. Supersedes the POLYLINE part of the 2026-10-01 line.
- **2026-10-03 (step 5.1d review, follow-up a).** ELK now loads in the PRODUCTION layout worker (Chromium, Firefox, WebKit; e2e in tests/e2e/smoke.spec.ts). Cause, confirmed in the pinned elkjs 0.12.0: `elk-worker` ends with `if (typeof document === 'undefined' && typeof self !== 'undefined') { self.onmessage = ... } else if (module.exports) { module.exports = { Worker } }`; in a web worker it concludes it IS ELK's own worker, installs its own `onmessage` and exports no `Worker`, so the bundled build threw "_Worker is not a constructor". Phase 4 only scanned the bundle and ran ELK under Node; it never ran the layout worker in a browser. Fix: `loadElk` (src/layout/elk/load.ts) gives the module an empty `document` for the first import and the first `new Elk()` (the bundle runs `elk-worker` lazily) and removes it in a `finally`, only in a worker scope. elkjs stays pinned and unpatched; no eval, no `new Function`, no CSP change, no nested worker; our RPC host listens with `addEventListener`, so it was never replaced, and the unit test (src/layout/elk/load.test.ts) proves `self.onmessage` stays ours.

### ADR-008 — Web workers with a small typed RPC
- **Requirements**: no main-thread task > 50 ms; cancellation; progress.
- **Decision**: four workers (chem, layout, search, compute) and a ~200-line typed RPC with cancel, progress, timeouts and restart.
- **Advantages**: explicit cancellation semantics; typed APIs; no magic proxies.
- **Disadvantages**: code to maintain.
- **Performance**: structured clone costs are bounded by sending ChangeSets, not whole states.
- **Maintenance**: contracts in `src/workers/rpc/contracts.ts`.
- **Migration implications**: none.
- **Why chosen**: cancellation and progress are first-class needs.
- **Rejected**: Comlink (no built-in cancellation/progress semantics; proxies obscure costs).

### ADR-009 — RDKit.js (MinimalLib) behind `StructureToolkit`
- **Requirements**: parse SMILES/molfiles, canonicalise, formula, stereo, SMARTS, depictions — offline.
- **Decision**: RDKit.js WASM in the chem worker, lazy-loaded, behind `StructureToolkit`; SVG depictions sanitised; facts cached by (input, toolkit, version).
- **Advantages**: the reference cheminformatics toolkit; high-quality depictions; SMARTS.
- **Disadvantages**: ~6 MB WASM; needs `'wasm-unsafe-eval'` in CSP.
- **Performance**: parse/depict in milliseconds; cached.
- **Maintenance**: only the adapter imports RDKit.
- **Migration implications**: toolkit swap = new adapter; cached facts invalidate by version.
- **Why chosen**: correctness of chemistry matters more than bundle size, and it loads lazily.
- **Rejected**: OpenChemLib JS (good and smaller; kept as the fallback adapter candidate); SmilesDrawer (drawing only, no chemistry model); Kekule.js (heavier, less maintained).
- **Implementation (step 4.3a, `@rdkit/rdkit` 2026.3.6 pinned; refines, supersedes nothing)**: only `src/chem/rdkit/` imports the package (`.dependency-cruiser.cjs`: `rdkit-only-in-adapter`), `loader.ts` alone; the adapter depends on structural types, so tests use a fake module. Input caps and the declared format are checked BEFORE RDKit (its `get_mol` sniffs its input). A failed call is a value: `invalid` (RDKit cannot read the structure: the only reason that means the structure is bad), `unavailable` (no module, a WASM trap, a failure while working on a structure it did read), `timeout` (the RPC client's: RDKit is synchronous, so a call past its 2 s limit is stopped by terminating the worker), and for depictions `refused`. A WASM trap (`WebAssembly.RuntimeError`, or a JS `RangeError`) drops the module; the next call loads a fresh one. Every RDKit object is freed in a `finally` through `withHandle`. Facts come from RDKit's own output and a fact it does not give is left undefined with a warning, never guessed. The cache (LRU 500 for facts, 500 for depictions, in the chem worker) compares the whole input on a hit, and never keeps `unavailable` or `timeout`. The SVG sanitiser is pure string work in `src/chem/svg` (docs/SECURITY.md §2).

### ADR-010 — Structure drawing: Ketcher adapter (architecturally supported)
- **Requirements**: optional drawing of structures without making it mandatory.
- **Decision**: text entry + live depiction now; `StructureEditor` interface in `src/features/workbench/structure-editor/` with a lazy Ketcher adapter as ARCHITECTURALLY SUPPORTED.
- **Advantages**: no heavy dependency until needed; users can author everything by text.
- **Disadvantages**: drawing is not available initially.
- **Performance / Maintenance**: zero cost until adopted; adapter isolated.
- **Migration implications**: none; structures are stored as text either way.
- **Why chosen**: anti-overengineering.
- **Rejected**: building a custom editor (enormous scope); bundling Ketcher now (size, CSP review needed).

### ADR-011 — MiniSearch + chemistry-aware normaliser
- **Requirements**: fast fuzzy/prefix search over names, aliases, formulas; incremental updates; offline; in a worker.
- **Decision**: MiniSearch with fields and boosts; normaliser in `src/core/text` shared with validation.
- **Advantages**: small, incremental add/remove, serialisable index.
- **Disadvantages**: no substructure search (RDKit handles that when needed).
- **Performance**: < 50 ms queries at 5k reactions.
- **Maintenance**: document builder is a pure function.
- **Migration implications**: index is a cache; rebuildable.
- **Why chosen**: incremental updates and size.
- **Rejected**: Fuse.js (linear scan, slow at scale); Lunr (immutable index, rebuild on every change); FlexSearch (fast but weaker typing and field-level control).
- **2026-10-01 (step 4.5).** minisearch 7.2.0. Prefix, fuzzy and exactness are set per query group (names and aliases; formulas; tags and text) through query-combination options rather than per index field, because MiniSearch applies them per query. Removal uses `remove`, not `discard`, so the index is a function of its documents; scores are rounded to 9 decimals because MiniSearch's BM25 averages drift by a few ulps with the add and remove history. Details: SEARCH §6.

### ADR-012 — Zustand for UI state
- **Requirements**: small, sliced UI stores readable outside React (viewport code).
- **Decision**: Zustand stores for selection, viewport, panels, filters, palette; canonical data stays in the core store.
- **Rejected**: Redux (ceremony); React context for everything (re-render storms); Jotai (fine, but atoms scattered across files are harder for agents to audit).
- **Other points**: negligible size and cost; no migration impact (UI state is tolerant and resettable).

### ADR-013 — Radix primitives, cmdk, TanStack Virtual
- **Requirements**: accessible menus, dialogs, tooltips; command palette; virtualised lists.
- **Decision**: Radix UI primitives (unstyled), cmdk for the palette, TanStack Virtual for lists.
- **Rejected**: MUI/Chakra (heavy styling systems conflicting with the visual language); hand-rolled a11y widgets (error-prone).
- **Other points**: tree-shaken; styled with our tokens; replaceable per component.

- **2026-10-03 (step 5.2, CSP spike; decision rule of note E3).** A throw-away page (not committed) was built with the production CSP and run in Chromium 153, Firefox 155 and WebKit 26.6 (Playwright 1.63.0), twice, keyboard-driven. Radix `Dialog` 1.2.0 with `modal={false}` plus `FocusScope` and our own `inert`; the native `<dialog>` with `showModal()`; Radix `DropdownMenu` 2.1.25 and `Popover` 1.2.0 non-modal; Radix `Tooltip` 1.3.0; a toast in a polite live region; React `style` props. Result: ZERO `securitypolicyviolation` events and no console error for every candidate in every engine. Native `<dialog>`: focus moves in, stays in the dialog (in Chromium and WebKit it may also leave the page to the browser's own UI; never to the background), the background is inert, Esc closes, focus returns (WebKit does not focus a clicked button, so the component remembers the click target). Radix Dialog: all the same, but the inert background is OUR attribute, not Radix's. Menu: arrows, Enter, Esc, focus back to the trigger. Popover and Tooltip: Esc, focus back. **Decision (both dialogs pass -> native): the Dialog is the native `<dialog>`; Menu and Tooltip are Radix, non-modal; no Popover in 5.2 (nothing uses it; the spike says it passes); Toast is our own component (no library).** `@radix-ui/react-dialog`, `-focus-scope` and `-popover` were not kept. `@tanstack/react-virtual` moves to step 5.5b (a primitive is built where it is first used). Known effect of the native modal: everything outside it, including a body-mounted Radix portal, is inert, so menus and tooltips opened inside a dialog mount inside it (`PortalContainerContext`).

### ADR-017 — Enforced module boundaries
- **Decision**: dependency-cruiser rules (`.dependency-cruiser.cjs`) + ESLint restrictions (no DOM/storage/network/nondeterminism in core; no HTML injection anywhere) + file-size and hardcode scripts, all in `npm run check`.
- **Why**: architecture that is not enforced erodes, especially with agents working session by session.
- **Amended 2026-10-02 (Phase 5 step 5.0, decision Q10/Q13)**: three more dependency-cruiser rules: `src/ui`, `src/render` and `src/features` import `src/persistence` and `src/workers` as types only (`presentation-not-persistence-workers`), import `src/chem`, `src/layout`, `src/search` and `src/io` as types only except an explicit allow-list of pure modules (`presentation-engines-types-only`: `src/search/palette/parse.ts` and each service's `contracts.ts`), and never import `src/core/validation/rules` (`presentation-no-validation-rules`); tests are excepted. ESLint adds `no-implied-eval`, `no-new-func` and `no-script-url` (off in tests, which feed hostile `javascript:` strings to the code under test on purpose), and confines `Worker`, `SharedWorker`, `indexedDB`, `IDBKeyRange`, `BroadcastChannel` and `navigator.locks` to `src/app`, `src/persistence` (which still gets `indexedDB` and `IDBKeyRange` injected), `src/workers`, `src/test-support` and tests. No behaviour change; each rule was proved with a throw-away violation.

### ADR-026 — Validation is layered, lifecycle-aware and read-only
- **Decision**: L1–L3 block commits, L4 advises, findings are stored apart, auto-fixes are explicit commands (VALIDATION_RULES.md).

### ADR-027 — Condition-variant selection is a `ProjectionRequest` field, not a `ViewFilters` field
- **Decision**: `ProjectionRequest.conditionVariantId?: ConditionVariantId` (`src/core/graph/contracts.ts`) narrows one reaction's participants and outcomes to those holding under a chosen variant (GRAPH_SEMANTICS.md §7, reaction_explorer). It is not on `ViewFilters` (`src/core/schema/presentation.ts`).
- **Why**: `ViewFilters` is persisted (`view_preset.filters`) and names a cross-reaction restriction (topics, reagent families, scope); a condition variant names a part *within* one focused reaction, so persisting it as a saved-view default would not generalise across reactions. Keeping it on the request avoids a schema change (`CURRENT_SCHEMA_VERSION` unchanged, no migration).
- **Consequence**: `Projection.key` (the cache key) hashes it (`kit.ts`); every other projection ignores it. Step 2.5 widened its use to `precursor_explorer` too (same rationale).

### ADR-028 — Degree-cap overflow is its own `EdgeSemantic`; the ⇌ badge reuses `relationshipId`/`relationshipType`
- **Decision**: `EdgeSemantic` (`src/core/graph/contracts.ts`) gains `'overflow'` for the synthetic edge into a degree-cap overflow node (GRAPH_SEMANTICS.md §11). The ⇌ badge (§5) is *not* a new edge or field: `precursor_explorer` tags the two produces edges of a mirrored `reverse_of` pair with the existing (until now unused) `relationshipId`/`relationshipType` fields.
- **Why**: an overflow edge stands for several collapsed neighbours, never one real participation or production, so giving it `'consumes'`/`'produces'` would be misleading and would need a `reactionId` it does not have; a distinct semantic makes that explicit and lets the INV-26 check skip it honestly (it already skips any edge with no `reactionId`). The ⇌ badge is a *relationship between two already-drawn edges*, exactly what `relationshipId`/`relationshipType` were declared for — a new field would duplicate that.
- **Consequence**: no schema change (`GraphEdge`/`EdgeSemantic` live in `src/core/graph/contracts.ts`, not `src/core/schema`); `graphEdgeId` still hashes the overflow edge's identity `(view, from, to, semantic)` with the rest absent, so the harness's generic "ID is the hash of its identity" check (INV-26) needs no exception for it.

### ADR-029 — `EdgeSemantic` gains `uses_mechanism`; classification edges from a reaction omit `reactionId`
- **Decision**: `EdgeSemantic` (`src/core/graph/contracts.ts`) gains `'uses_mechanism'` for the `mechanisms` view (a reaction/outcome linking a mechanism), mirroring the already-scaffolded-but-unused `'uses_reagent'`. Separately: a `membership` edge from a reaction (to a topic, or to a named-reaction family) and a reaction-level (no `outcomeId`) `uses_mechanism` edge never set `GraphEdge.reactionId` — only an outcome-level `uses_mechanism` edge does (an outcome names at most one mechanism, so it stays unique).
- **Why**: INV-26 treats any edge with `reactionId` set as naming exactly one real participation or production, and requires it to be unique *regardless of endpoints* ("whatever their endpoints" — GRAPH_SEMANTICS.md §10). A reaction can validly carry several topic mappings, several named-reaction families, or several reaction-level mechanism links — these are classifications, not participations/productions, and setting `reactionId` on them made two legitimately distinct classifications of the same reaction collide under that check. The projection harness caught this immediately: the first run of `syllabus` over the demo's one cross-chapter reaction (docs/JEE_ONTOLOGY.md's diazonium → phenol) reported an INV-26 violation.
- **Consequence**: no schema change. The reaction is still recoverable from `edge.from` on every such edge (they are always drawn *from* the reaction). Consumes/produces/transforms_to/uses_reagent edges are unaffected — a participant or outcome/product *is* inherently unique per reaction, so `reactionId` stays exactly as documented for those.

### ADR-030 — `ReadonlyIndexes.navigatorRollup()`: the navigator's hub roll-up moves into `core/indexes`
- **Decision**: `ReadonlyIndexes` (`src/core/indexes/contracts.ts`) gains `navigatorRollup(): NavigatorRollupIndex` — every reaction's precomputed navigator hub-level contribution (source/target hubs, per-outcome main-product candidates, Unclassified/Unanchored membership), aggregated per hub (`candidatesFrom`/`candidatesTo`, `src/core/indexes/navigator-rollup.ts`), maintained incrementally by `IndexEngine.apply` the same way the other cross-record tables are. Hub resolution itself (`HubResolver`, `hubTargets`) and the "what does this reaction carry" selection (`primarySubstrateOf`/`mainProductsOf`) move from `src/core/graph/navigator/{hubs,select}.ts` into `core/indexes` with them; the graph-layer files become thin re-exports/wrappers so every existing caller (`build.ts`, `precursor/reverse-of.ts`) keeps its old signature.
- **Why**: the navigator's projection build scanned every reaction in the state on every call (GRAPH_SEMANTICS.md §3's whole-dataset hub overview, not a local seeded traversal) — measured at 21.81–27.2 ms at the design tier against the 16 ms budget (Gate B packet §5), and worse once benchmarked on p99 with realistic sample counts. Maintaining the hub-level candidates incrementally (only touched reactions recomputed on a plain edit; only the reactions referencing a species/reagent recomputed on a class-membership change; the whole roll-up rebuilt, but only *this* index, on an anchor/class-hierarchy/display change) turns `build()`'s cost from proportional to total reactions into proportional to hub count and output. Doing this inside `core/indexes` rather than `core/graph` is not a style choice: `core/graph` already imports `core/indexes`, so `core/indexes` importing anything from `core/graph` would be a cycle (`no-circular`, `.dependency-cruiser.cjs`) — the hub-resolution logic itself had to move down, not be duplicated.
- **Consequence**: additive only — `CoreIndexes` and every other `ReadonlyIndexes` member is unchanged, no schema change, no `CURRENT_SCHEMA_VERSION` bump, no migration. `src/test-support/navigator-reference.ts` keeps the pre-2.9 full-scan algorithm as a differential-test oracle. One real behaviour change, deliberate and documented in the same commit: which specific edges survive a `maxEdges` truncation is now an explicit, stable sort by `(reactionId, outcomeId, productId)` in both the index-backed build and the reference — previously an undocumented accident of scanning reactions in ID order, which stopped matching once candidates were gathered hub-by-hub instead.

### ADR-031 — `ValidationRule.referencedReads`: field-aware scope for referrers in `validateTouched`
- **Decision**: `ValidationRule` (`src/core/validation/contracts.ts`) gains an optional `referencedReads?: ReferencedReads` — for each kind of record the rule's subject refers to (or `'*'` for any kind), the top-level fields the rule's `check` reads of it; `[]` means "only whether it exists", an absent kind means "not read". `scopeOf`/`validateTouched` add a referrer of a touched record only if some L2/L3 rule of the referrer's kind reads a field that changed, or the record was created or deleted (everything about it changed). A rule that does not declare it keeps the old behaviour: it re-runs on any change to a referenced record. `previous` (already a parameter) supplies the diff; without it nothing can be diffed and every referrer is kept.
- **Why**: `scopeOf` expanded a touched record to every referrer at record-kind granularity (docs/PERFORMANCE_ARCHITECTURE.md §4, PROGRESS.md step 2.10), so renaming a species used by 1,000 reactions re-validated 1,000 reactions to learn that none of their rules read a species' name. Measured at the design tier: 65-94 ms per commit on a 1,000-referrer hub, against a 16 ms budget. `watches`/`peers` are kind- and record-level and cannot say which fields matter; the declaration is the missing field-level half.
- **Consequence**: additive; no schema change, no `CURRENT_SCHEMA_VERSION` bump, no migration. Narrows only the *referrer* expansion. The referent expansion (a touched record's own references, which RXN-018 and AST-001 depend on) and every `peers`/`watches` path are unchanged, so anything a rule reads outside its own references stays covered exactly as before. Scope stays whole records: `FindingStore.replaceForSubjects` replaces a subject's findings per level, so a subject is either fully re-validated or left alone; per-rule re-runs on a referrer would need a finding-merge contract and remain a Phase 9 candidate (*done in ADR-032, step 2.13, which adds that contract*). A declaration is a promise about `check`, verified mechanically (`src/core/validation/reads-audit.test.ts`: a read trace of every declared rule over the maximal fixture, the demo and every generator shape, and a "referenced records vanish" differential for rules declared to read nothing) and by the incremental ≡ full property test on hub states (`tests/property/validation-scope.test.ts`). Declared only where the reads are exact: every `scope: 'record'` rule, the REF rules, RXN-013, RXN-018, REL-003/005/006, SPC-001/005, CLS-001/002, HIER-002, CUR-003…006, PRS-001/002, AST-001, RVW-002. Left undeclared (they walk hierarchies or routes through derived indexes): SPC-006, HIER-001, HIER-003, RTE-002, RTE-004. *Superseded in part by ADR-032 (step 2.13): scope no longer has to be whole records, and SPC-006 is now declared.*

### ADR-032 — `FindingStore.replaceForRules` and `Validator.validateTouchedByRule`: per-rule re-validation of referrers and peers
- **Decision** (the reviewer approved an additive `FindingStore` change): `FindingStore` (`src/core/validation/contracts.ts`) gains `replaceForRules(subjects, ruleIds, findings)`, which replaces, for each subject, only its findings of the listed rules (at whatever level) and leaves every other finding of that subject alone; `replaceForSubjects` is unchanged. `Validator` gains `validateTouchedByRule(state, indexes, touched, previous, known)` returning a `TouchedValidation`: `scope`/`findings` (subjects re-validated whole, committed with `replaceForSubjects`) and `byRule` (subjects of which only some rules were re-run, committed with `replaceForRules`), plus `all`. `commitTouched(store, result)` does both. `scopeOf` and `validateTouched` keep their meaning (whole subjects; `scopeOf` = `scope` plus the `byRule` subjects), so existing callers are unaffected. The command store now makes this one call per commit.
- **Rule**: the touched records, their referents, and any referrer or peer with an affected **L2** rule are re-validated whole. A referrer whose rules that read a changed field (`referencedReads`, ADR-031) are all L3 has only those rules re-run; a peer named by an L3 rule has only that rule re-run (`peers` already means "records whose findings *for this rule* can change"; this is a reading of that sentence, applied here for the first time, and goes one step beyond the referrer case the reviewer named). L2 rules stay whole because an L2 ERROR gates a record's L3 rules off (VALIDATION_RULES.md §1), so a changed L2 outcome can add or remove every L3 finding. A per-rule subject that currently has an L1/L2 ERROR in `known` (the store the result is committed to; `bySubject`) is skipped: it has no L3 findings, and its L1/L2 outcome cannot have changed or it would have been whole.
- **Why**: after ADR-031 a hub edit that touches no field its referrers read is free, but one that does (a species' `review`, read by RVW-002) still re-ran all ~1,000 referrers whole (~50 ms of the 67-77 ms commit measured in step 2.12/2.13) although one rule of about forty was affected; likewise a class listed by 1,400 species re-validated every species whole through SPC-006's peers.
- **Consequence**: additive; no schema change, no `CURRENT_SCHEMA_VERSION` bump, no migration. The incremental ≡ full guarantee is unchanged and tested three ways: the hub/class-hub property test (`tests/property/validation-scope.test.ts`, now with review-status and class-hub edits), the fixture random walks on both commit paths (`incremental.test.ts`), and `scoping.test.ts` (a referrer's findings from rules that did not run survive; a referrer with an L2 ERROR is left alone). SPC-006 is now declared (`class: ['parentIds']`): its reads go through the class-ancestry index, so `reads-audit.test.ts` was extended to treat a walk up from a record the subject refers to as a read of that kind's parent field (a wrong declaration fails it). Removes the doubled `scopeOf` call as a side effect (the store calls one method). **Addendum, same step (reviewer-approved): `ValidationRule.peerReads?: ReferencedReads`**, the mirror of `referencedReads` for `peers`: which fields of a touched record (keyed by its kind, or `'*'`) the rule reads of it when validating one of its *other* records, outside that record's own references (a name twin, a class ancestor, a species listing a class). `peers` is called for a touched record only if a listed field changed, or the record was created/deleted; undeclared means today's behaviour (called on every touch). Without it touching a class re-ran SPC-006 on every species that lists it (or a descendant) even when only its name changed (1,400 species at the design tier, ~30 ms of a ~38 ms commit). Declared where the reads are exact: SPC-001 (`species: names`), SPC-005 and CLS-002 (`class: names`), SPC-006 and CLS-001 (`class: parentIds`), HIER-001 (each hierarchy kind's parent field). Left undeclared: REF-006, REF-008, REL-003/005, CUR-004/006, PRS-001/002, HIER-003, RTE-002, RTE-004. Verified by the read audit (the reads such a rule makes of records it does not refer to — direct fetches, name-index lookups, hierarchy walks — must be listed; it refuses index lookups through other records' reference fields) and by the property tests, both fault-injected. Named `peerReads` (not `watchedFields`) to read as the counterpart of `referencedReads`.

### ADR-033 — Follower tabs mirror the writer: `applyRemote` and `reload` on a read-only store
- **Decision** (Phase 3 contract decisions Q3/Q11, reviewer-approved; supersedes nothing, completes ADR-005): `CanonicalStore` (`src/core/commands/contracts.ts`) gains `applyRemote(change: RemoteChange)` and `reload(state, revision)`. A `RemoteChange` is `{ fromRevision, revision, upserts, deletedIds, meta? }`: the records the writer changed, as stored at `revision` and already L1-parsed, and the IDs that no longer exist. `ChangeSet.cause` gains `'remote'`, `CommandErrorCode` gains `'NOT_FOLLOWER'`, and the core index engine accepts a `'remote'` ChangeSet as a forward span (a writer transaction may cover several revisions; no other cause may skip one). Persistence (`src/persistence`) adds the ports `WriterLock` (`acquire` may answer `'unsupported'`; `whenAcquired`) and `ChangeChannel`, the message `ChangeMessage { fromRevision, revision, changedIds }` (`changedIds` may be `'all'`), the Web Locks / BroadcastChannel implementations (`web-locks.ts`, handed their browser objects from outside), the follower controller (`follower.ts`), `adapter.promote()` and `attachWriteQueue` (`write-wiring.ts`). `OpenResult.bootReport.singleTab` reports a browser without Web Locks.
- **Guards** (INV-28: exactly one tab writes). (1) `applyRemote` and `reload` are allowed only while the store is read-only (a follower); on a writable store they are **refused as a value** (`NOT_FOLLOWER`), never applied. (2) A follower has **no write queue attached**: `attachWriteQueue` refuses a read-only store as a value, and the adapter's queue is read-only until promotion. (3) A ChangeSet with `cause: 'remote'` is never written, whatever the wiring: a second guard, not the main one. (4) Re-validation uses `validateTouchedByRule` **with the previous state** (ADR-032), the same incremental path as a local commit. (5) `applyRemote` applies only when `fromRevision` equals the store's current revision (`STALE_REVISION` otherwise: the follower reloads fully, never guesses). (6) `reload` adopts the state at the revision storage holds (not revision + 1) and **clears history**. (7) **Promotion = reload, then writable**: the write queue becomes writable and boot runs again as the writer (migration, quarantine move, markers, crash check), the store reloads from that result while still read-only, and only then does the tab become writable and get a write queue. A refused promotion leaves the tab read-only. Read-only becomes switchable only through promotion.
- **Amended 2026-10-18 (step 6.1b part 2, openItem 23): `ChangeSet.reloaded?: true`.** `reload` marks its `'remote'` ChangeSet `reloaded: true`; `applyRemote`'s ChangeSet has no marker. Derived consumers analyse an unmarked `remote` ChangeSet (one mirrored writer transaction, possibly several revisions, its lists naming every record that differs) like a commit, and a marked one as a whole state (full load / build). The search sync and `DerivedIndexes` do so; the compute replica sync already forwarded `remote` ChangeSets incrementally. Additive; no schema change.
- **Why**: the store has to follow another tab's commits without becoming a second writer and without the cost or the semantics of `replaceState`: `replaceState` refuses while read-only, validates the whole state on every call (about 2 s at the design tier) and assigns revision + 1 instead of adopting the writer's revision. IndexedDB is the source of truth, so the message carries only `{ fromRevision, revision, changedIds }` and the follower re-reads the rows: the channel stays small and bounded, ordering and lost messages are detected by the revision chain, and a row is validated (L1) by the tab that uses it.
- **Consequence**: no ERROR gate on a mirror: the writer already accepted the state and it is durable, so errors become findings (visibly, in the finding store), never a reason to refuse or to show stale data. A message that cannot be applied incrementally for any reason (gap, moved database, row failing L1, store failure, backlog beyond 100) is a full `reload` (about 2 s at the design tier by the step 3.3 boot parts: read 0.4 s, L1 0.4 s, indexes 0.45 s, `validateAll` 0.8 s, measured for boot, not for a reload; main thread until Phase 4, which must let `reload` take precomputed findings and prebuilt indexes: IMPLEMENTATION_PLAN.md Phase 4 notes). A follower never writes, so it never quarantines: a row that fails L1 is reported and left out, and only the writer's boot or promotion moves it. The follower's apply of a hub edit costs about what the writer's own commit of it cost (PROGRESS.md step 3.4). Alternatives rejected: reusing `replaceState` for followers (above); letting a follower write its own view and reconcile (INV-28, ADR-005: silent loss); shipping patches over the channel (unbounded, ordering-sensitive, and the database would still have to be re-read after any gap); keeping a follower-side write queue that ignores `remote` (guard 3 is only the backstop).

### ADR-034 — Worker model and RPC rules: stateless engines, one replica, terminate to stop, retry once
- **Decision** (Phase 4 plan review D1 and D4, contract decisions 2026-09-30; refines ADR-008, supersedes nothing): (1) The chem and layout workers hold **no state**; the compute worker holds the **only replica** of the canonical state; the search worker holds a derived index (a cache, rebuildable). (2) The engines that run synchronously (RDKit, ELK) cannot see a cancel, so a call is stopped by **terminating its worker**: cancel means "drop the result". (3) Persistence stays on the main thread (one write queue, INV-28); worker entries import core and their own service only (the compute entry also io), never persistence, ui or features (`.dependency-cruiser.cjs`: `workers-not-persistence`, `services-not-workers`, `worker-entry-*`).
- **RPC rules** (`src/workers/rpc`): a client call answers a value, `RpcResult<T>` (`{ ok, value }` or `{ ok: false, error }`), and never rejects (CLAUDE.md §6; a small amendment to the `RpcClient` type of ADR-008's contract, which returned bare promises). A cancel answers `CANCELLED` at once, sends `cancel` to the host (it aborts the call's `AbortSignal` and sends no answer), and a response that arrives anyway is dropped and reported (`dropped_response`). A per-call timeout answers `TIMEOUT`, **terminates and restarts** the worker and fails every other pending call with `WORKER_CRASHED` (the worker's state is gone with it; those calls are victims of the restart, so `callWithRetry` may retry them if idempotent). A crash (`error`, `messageerror`, `exit`) fails every pending call with `WORKER_CRASHED`, then restarts. Restarts are capped: `maxRestarts` (default 3) counts restarts **in a row**, reset by any successful response; beyond it the client stays down and every call answers `WORKER_CRASHED` as a value. After each restart `onRestart(raw, info)` runs (the caller reloads its replica through `raw`, which does not wait); every other call waits for the hook; a hook that fails is reported (`restart_hook_failed`) and calls proceed (the compute worker answers `NOT_READY` until a replica is loaded); a hook that does not finish within `restartHookTimeoutMs` (default 30 s) is reported (`restart_hook_timeout`), the restart counts as failed towards `maxRestarts`, the calls waiting for it answer `WORKER_CRASHED` and the worker is terminated and started over. When the client gives up (restart cap reached, or no worker can be created) it emits `gave_up`: being down is never silent. At most `maxInFlight` calls (default 16) are in flight; the next answers `BUSY` (reported). The host has its own cap (64), answers `BAD_REQUEST` for an unknown method or a repeated ID, and `INTERNAL` with the exception's **message only** for a throwing handler. Every param and result is structured-cloneable; buffers are moved with `transfer` (request) and `withTransfer` (result), never copied when large.
- **Retry once (D4).** `callWithRetry` retries a call a second time only when the first answered `WORKER_CRASHED` (the client has restarted the worker and the hook has run) and the method's spec says `idempotent`: `validateAll`, `findRoutes`, `importPreview`, the export build, `parse`, `depict`, `layout`, `search`. Never for apply-like calls, never after `TIMEOUT` (a call that timed out would most likely time out again; only a call that was a victim of someone else's restart, `WORKER_CRASHED`, is retried), never after `CANCELLED`. **A retried preview gets a new `batchId`:** the pending import batch lived in the crashed worker, so `importRevise`, `importCancel` and apply on the old `batchId` answer `UNKNOWN_BATCH` (a value); the UI shows that the preview was lost, never a half-applied import.
- **Default timeouts (approved by the reviewer, step 4.1 review, 2026-09-30).** A timeout costs a restart and the worker's state, so the defaults are about ten times the budget row (`docs/PERFORMANCE_ARCHITECTURE.md` §2): a slow machine must not look like a hang. Chem and layout: **2 s per call** (fixed by D1 and ADR-007/009). Compute (proposed): `loadReplica` 30 s (clone + index build about 2 s at the design tier), `validateAll` 30 s (budget 3 s), `applyChanges` 5 s, `adoptPending` 5 s, `findRoutes` 5 s (bounded traversal), import `preview`/`revise`/`prepareApply` 60 s (budget 5 s), `importCancel` 2 s, `exportPlan` 10 s, `exportBuild` 30 s (budget 2 s), `snapshotBuild` 30 s (0.4-0.8 s at the design tier), `snapshotDecode` 60 s (restore about 3.5 s before the move). Search (proposed): `load` 30 s (build budget 1.5 s at 5k reactions), `apply` 5 s, `search` 2 s (budget 50 ms: only a hang takes 2 s), `serialize` 30 s. Each step that adds a method sets its own `RpcMethodSpec` from this table; a `timeoutMs` per call overrides it.
- **Ports and tests.** The client works over an injected `RpcPort` and `WorkerFactory` (browser `Worker`: `browserWorkerPort`; Node `worker_threads`: `src/test-support/rpc-node-port.ts`); the host over an `RpcMessagePort`. Tests use an in-memory port pair that clones every message with `structuredClone` and, for the real thing, a `worker_threads` fixture running the real host under tsx. Creating workers in the app is Phase 5 (D7).
- **Precomputed findings (Q3, step 4.2a).** `replaceState` and `reload` take optional `PrecomputedFindings { findings, ruleSet, revision, recordCounts }` from the compute worker. `RULE_SET_ID` is computed in core from the sorted (rule ID, level) pairs of the L1 schema rule and the registered L2 and L3 rules (never hand-edited; the rule order and the severities do not matter). The store accepts the findings only if the rule set is its own, `revision` is the revision it will adopt (`replaceState`: current + 1; `reload`: the argument), the record counts equal the new state's, every finding is about a record of the new state, is level 1-3 of a rule of that level in the rule set, and no finding ID repeats; otherwise `FINDINGS_MISMATCH` as a value with the failed check named, and store, history and findings are unchanged. Never a silent recompute. The ERROR gate of `replaceState` runs on the precomputed findings; `reload` keeps ADR-033 (no gate). Indexes are still built on the main thread (D2). The option `verifyPrecomputed` (default false, tests only) also runs `validateAll` and refuses if the results differ, which is how the property test proves precomputed = in-process. What no cheap check can prove, that no finding is missing, rests on the worker computing `validateAll` on the replica of exactly that revision (step 4.2b).
- **Compute replica and its sync (step 4.2b).** The replica (`src/workers/compute/replica.ts`) follows the store by applying the SAME ChangeSets through the same paths as the store's commit step: Immer patches, then the index engine's `apply`, then `validateTouchedByRule` ALWAYS with the previous state and the replica's own finding store as `known` (Phase 9 exception 5 must never be the worker's path; a validator spy test proves it for every ChangeSet cause). It holds the FULL index engine (route search needs the cross-record indexes; the store keeps the part-1 engine). `loadReplica` answers the `PrecomputedFindings` the store accepts (validateAll, `RULE_SET_ID`, revision, record counts). `applyChanges` answers `{ ok: true, revision }` or the value `{ ok: false, code: 'REPLICA_STALE', have }` when the ChangeSet is not one step ahead (a `'remote'` one may span revisions, as in the core index engine); `validateAll` and `findRoutes` (which now takes `{ revision, query }`) answer the same refusal when the revision asked is not the replica's; a call before the first load is `NOT_READY`. Idempotent: `loadReplica`, `validateAll`, `findRoutes`; `applyChanges` is NOT (a repeat would fail the revision check or double an edit). `findRoutes` times its budget with an injected clock. The main-thread sync (`createReplicaSync`) subscribes to the store and forwards every ChangeSet in order, ONE at a time; it sends ONE `loadReplica` of the store's current state instead of forwarding when the worker answers `REPLICA_STALE` or any other refusal, or when more than 100 ChangeSets or 2,000 touched records are waiting (measured: an ordinary edit is about 1-2 ms in the worker, a hub edit about 0.4-1 ms per touched record, a reload 1.3-3.1 s); after a crash or timeout the client's `onRestart` hook reloads from the store's current state before any other call is sent, and a queued ChangeSet already inside the loaded state is dropped (contained, not lost). A client that gave up, or a reload the worker refuses, is `down`. Status (`in_sync`, `reloading`, `down`) is a value and a `replica_status` WorkerEvent. `adoptPending` is built with the first producer of a pending state (import), step 4.2c.
- **Import in the compute worker, adoption and snapshot bytes (step 4.2c).** The import session (`createImportSession`, unchanged Phase 3 code) is hosted in the worker (`src/workers/compute/import-host.ts`); the live dataset it compares against is the REPLICA, and the pending batch (at most one) lives in the worker, so a crash loses it and the next call on it answers `UNKNOWN_BATCH`. Calls: `importPreview({ source: Blob, fileName, request?, ids })`, `importRevise({ batchId, request, ids })`, `importCancel`, `importPrepareApply({ batchId, plan, baseRevision })`. They run one at a time. `ids` is `{ nowIso, seed }` (`IdData`): the worker rebuilds an `IdFactory` from it per call, so it has no clock or random source of its own for IDs; main supplies a NEW seed for every call. A revise or prepare against a replica that is not at the revision the preview was built on is refused as a value (`STALE_REVISION`, the batch consumed). `prepareApply` (the pure half of Phase 3 apply, `src/io/import-prepare.ts`) makes the same refusals as `apply` and returns `{ mergedState, precomputed, report, quarantine, assets }`: `precomputed` are `validateAll` findings of the merged state stamped for `baseRevision + 1` (what `replaceState` takes), `report` and `quarantine` lack only what the applier knows (time, snapshot ID), and the asset buffers are TRANSFERRED (a Blob source is shared by structured clone, it cannot be transferred). The worker builds the merged state's replica (index build + `validateAll`, once) and keeps it as the replica's PENDING state (`replica.prepare`); `adoptPending({ revision })` swaps it in, `dropPending` forgets it; a refusal is a value (`NO_PENDING`, `PENDING_REVISION`, `REPLICA_STALE`) and the sync then reloads. A batch whose asset bytes already left is used up by the apply, whatever its outcome (its buffers are detached); a batch without assets stays pending after a failed apply, as in Phase 3. **Main side** (`src/workers/compute/import-flow.ts`, ports only, never persistence): wait for the sync to settle, prepare, `snapshotBuild({ revision, reason, exportedAt })` (bytes built from the replica, transferred; `exportedAt` is main's wall-clock time because the worker's clock is monotonic), the persistence bytes entry point `storeSnapshotBytes` (stores the bytes as they are, refuses as a value when their revision is not the adapter's current revision, i.e. the newest revision its write queue was given), `sync.expectAdoption(revision + 1)`, ONE `store.replaceState(merged, 'import', precomputed)`, then the batch report and quarantine rows. The Phase 3 checks stay: STALE_REVISION before and after the snapshot, UNKNOWN_BATCH when the batch was cancelled or replaced while the snapshot was written, and any refusal deletes the snapshot and changes nothing. When the sync sees the `replace` ChangeSet at the announced revision it sends `adoptPending` instead of forwarding the ChangeSet, so the merged state crosses the boundary once (back to main) and not twice. **Duplication, on purpose:** a worker never imports persistence, so `snapshot-build.ts` repeats the few lines of `buildSnapshot` (document, deterministic JSON, zlib level 6); `snapshot-build.test.ts` proves the bytes equal the codec's byte for byte and decode with it. **Rejected:** an injected `SnapshotBuilder` (a function cannot cross the boundary; reviewer decision Q1); moving the codec to a shared package (a new layer for 15 lines).
- **Snapshot restore, boot and follower in the compute worker (step 4.2d).** `snapshotDecode({ bytes, id, schemaVersion, baseRevision })` decodes the stored bytes (the same bounded inflate and envelope check as `decodeSnapshot`), migrates them with the worker's injected runner, parses strictly, and prepares the state as the PENDING one (indexes and `validateAll` once); it answers `{ ok: true, state, precomputed, steps }` or the Phase 3 codes (`CORRUPT`, `MIGRATION_FAILED`, `INVALID`), plus `REPLICA_STALE` and `BUSY` (one pending state at a time: a prepared import refuses a decode and a decoded snapshot refuses `importPrepareApply`). The persistence adapter gains `readSnapshotBytes(id)` (the stored bytes, size-checked, not decoded). `createComputeRestore` (main side, ports only): read bytes, settle the sync, decode in the worker, `pre_restore` through `snapshotBuild` + `storeSnapshotBytes` (taken again, at most 3 times, when the live data changed; the decode is redone for the new revision), expect the adoption, ONE `replaceState(state, 'restore', precomputed)`; every failure is a value with the Phase 3 code and changes nothing, the replica included; the `pre_restore` snapshot is removed on a store refusal. Boot: `BootPorts.validate(state, revision)` (optional, default in process) returns `PrecomputedFindings`; `open()` builds NO indexes when it answers (the store builds them once, `createCanonicalStore({ precomputed })`); an answer that fails `checkPrecomputed`, a rejection or a worker that cannot start makes boot validate in process, and `bootReport.validation { where, reason }` and a `validation_fallback` WorkerEvent say so. The migrated path awaits the port before `replaceAll` and keeps its ERROR gate. `createBootReplica` implements the port with `loadReplica` and hands its client and revision to `createReplicaSync({ adopt })`, so the replica is loaded ONCE; a follower's reload and a promotion use the same port and tell the sync (`noteLoaded`) so the reload's ChangeSet is not forwarded to a replica that already holds it. The decode code repeated in the worker is guarded by tests/integration/snapshot-decode-equality.test.ts (values, messages and the size cap equal the codec's).
- **L4 checks (step 4.3b).** The chem worker stays stateless: `checkSpecies`, `checkReaction`, `checkMechanism` and `matches` take the records' structures in batches (at most 64 items a call; the service sends 32) and answer plain data per item. The main side (`src/workers/chem/l4`, ports only: state, finding store, the chem service, a debounce) decides what to re-check from each ChangeSet, batches, merges by rule with `replaceForRules`, drops a result whose record changed again (request signature compared), remembers inputs the toolkit crashed or hung on (key: input + toolkit version; bounded, in memory on main, so a worker restart does not forget) and never sends them again until they change. A batch that times out is resent item by item (the culprit is the one that times out alone). Level-4 findings of records that no longer exist are cleared in the store's commit step (Q10 b).
- **Layout worker (step 4.4).** elkjs 0.12.0 (pinned; `npm audit` 0), its BUNDLED build (`elk.bundled.js`, no `eval`, no `new Function`, no `Function(`: scanned) running in OUR layout worker, one fresh instance per layout, never ELK's own worker; only `src/layout/elk/load.ts` imports it (dependency-cruiser `elk-only-in-adapter`). `LayoutRequest` is refused as a value when not sorted by id (nodes and edges, strictly ascending), malformed, or over **2,000 nodes / 4,000 edges** (`TOO_LARGE`). The worker answers ELK's result, or the in-house fallback (longest-path layering after DFS cycle breaking, 8 barycentric sweeps, straight routes) with `fallbackReason`: `elk_error` when ELK throws, `engine_unavailable` when it cannot load, `timeout` when the main-side service asked the NEW worker for it (`layoutFallback`) after the 2 s limit terminated the old one. If no worker can answer, the service returns `UNAVAILABLE` as a value: there is never a layout on the main thread. The service caches results by `cacheKey` (LRU of 32, memory only; persistence is Phase 5; only ELK's and the `elk_error` fallback are cached) and a newer request for the same view cancels the older (its result is dropped; a running ELK finishes in the worker). What each ELK algorithm honours is the table at the top of `src/layout/elk/map-request.ts`; whatever it cannot honour is listed in `LayoutResult.notes`. `cacheKey` now hashes everything that changes the answer (endpoints, hints, pins, `previous`), not just ids and sizes. ELK radial needs a tree (it throws otherwise, measured): the adapter gives it a spanning tree and routes the other edges straight; radial and stress ignore node sizes, so overlapping results are scaled apart (`spread.ts`) and a result needing more than 20x is an ELK failure. **Measured limits** (PROGRESS.md step 4.4): ELK layered on 400-node projections is about 0.55 s on the development machine (row: < 300 ms), a 60-node / 800-edge dense navigator takes about 3.5 s (over the 2 s limit), stress is all-pairs (100 nodes about 4 s).
- **Search worker (step 4.5).** minisearch 7.2.0 (pinned; `npm audit` 0; scanned: no `eval(`, `new Function`, `Function(` or string timers), imported only by `src/search/engine/` (dependency-cruiser `minisearch-only-in-adapter`). The worker holds the index and nothing else: `load` (replace), `apply` (answers `{ ok, revision, upserted, removed }` or `REVISION_MISMATCH` with `have`, -1 when nothing is loaded), `search` (`NOT_READY` until a load, never an empty list passed off as an answer), `serialize`, `loadSerialized` (`BAD_INDEX` as a value). Specs: `apply` is not idempotent (never retried after a crash; the restarted worker answers a mismatch and the sync loads), the others are, `search` 2 s, `apply` 5 s, the rest 30 s. The main side is a service (a newer query on a channel cancels the older: `CANCELLED`) and a sync over ports (state, the full indexes, the store revision, the service, a debounce): it rebuilds changed records and the documents whose derived data moved (`fanout.ts`), 500 dependent documents at a time with a backlog behind them, sends only documents that differ from the last one sent, and loads the whole state again on `replace`, `remote`, a mismatch or a worker failure. Documents never hold another record's text (SEARCH §6).
- **Amended 2026-10-02 (Phase 5 step 5.0, contract decision Q7, note E4): engine start-up has its own limit.** `warmUp(params: {})` is added to `ChemWorkerApi` and `LayoutWorkerApi` (additive). It answers a value, `{ ok: true, loadMs }` (from the handler's injected clock) or `{ ok: false, reason: 'engine_unavailable', message }`, never an `RpcError` for an engine that cannot load; it is idempotent (a loaded engine answers at once; the chem handler awaits the toolkit, the layout handler loads ELK) and its spec limit is `ENGINE_LOAD_TIMEOUT_MS` = 20,000 ms (to be revisited once step 5.1d has a real-browser number). The 2 s limit now covers CALCULATIONS only. The main-side services send `warmUp` before their FIRST REAL CALL (first need, not at creation, because the engines load lazily) and hold every call behind that one request (`createWarmUpGate`, `src/workers/rpc/warm-up.ts`; the client is created with `onRestart: gate.onRestart`). `ok: false` is kept for the life of the gate: chem calls answer `unavailable` with the message, layout answers the fallback layout (`engine_unavailable`), and nothing restarts. A warm-up TIMEOUT is an ordinary RPC timeout (the worker is terminated and restarted, the restart counts towards `maxRestarts`, `gave_up` is a status); the gate then returns to cold and the next call tries again. `onRestart` sends `warmUp` to the new worker again only if the engine had been warmed. `firstCallTimeoutMs` was rejected. Optional `LayoutEngine.warmUp()` (an engine with nothing to load omits it). No schema change.
- **Amended 2026-10-02 (Phase 5 step 5.1b, contract decisions Q7, Q8, Q9): the app wires the engines.** (chem) `SpeciesCheckResult.formula?` (additive): the formula the toolkit derived from the structure; the L4 service keeps it per species in memory (`derivedFormulaOf`, `subscribeFormulas`; dropped as soon as the species' structure changes or the toolkit does not answer), never as canonical data. `L4Service.summary()` (counters, no scan) feeds the status line. (layout) a fallback layout and the layout notes are reported in the event log and as the last notice in AppStatus. (search) `SearchDocument.derivedFormula?` (species only, indexed with `formula`: one field, boost 3, exact; configuration id 2, so an index serialised under 1 is `BAD_INDEX` and loads once), `DocumentPorts.derivedFormulaOf`, `SearchSync.refresh(ids)`, `SearchSync.adopt(revision)` (true only while the store is still at that revision; afterwards every rebuilt document and every removal is sent, because the sync cannot know what the cache held), `SearchSyncPorts.derivedFormulaOf` / `onStatus`. The warm-up gate gains `retry()` (unavailable -> cold, on a user action only), `message()` and `subscribe()`. Worker threads are created at their FIRST NEED by lazy clients (`src/app/services/lazy-client.ts`): chem at the first L4 run, layout at the first layout request, search at the boot decision (cache read or load); a missing factory is a status (`absent`). No schema change.
- **Why**: the replica lives in exactly one place, so restart and reload are one story; a synchronous engine cannot be interrupted cooperatively, so terminating is the only honest cancel; a retry that could apply a change twice is worse than an error. **Consequence**: a worker's timeout or crash always loses its state; the caller's `onRestart` reloads it (the whole state crosses the boundary once, D3). **Rejected**: cooperative cancel for RDKit and ELK (no hooks); a shared replica in a `SharedArrayBuffer` (cross-origin isolation, complexity); retrying every call (double apply); a Proxy-based client (Comlink, ADR-008).

### ADR-035 — CSP: no `unsafe-eval` on the page; `new Function` only inside the chem worker, from RDKit's glue
- **Decision** (reviewer, step 4.3a review, 2026-09-30; refines SECURITY §4, supersedes nothing): (1) The page policy stays exactly as SECURITY §4 says: `'wasm-unsafe-eval'` and **no `'unsafe-eval'` anywhere on the page**. (2) RDKit's embind glue builds its call wrappers with `new Function` (two sites, no `eval`). That is accepted **only inside the chem worker**, never from data (the wrapper source is built from the glue's own type signatures), and the chem worker has no DOM and no storage. Our own code keeps the ESLint ban on `eval` and `new Function`. (3) Every worker entry (compute, chem, later layout and search) calls `z.config({ jitless: true })` before anything else, like the page (`src/workers/zod-jitless.ts`, imported first). (4) The 4.6 build smoke fails if `new Function`, `Function(` or `eval(` appears in any built chunk other than RDKit's own chunk. (5) Phase 5 (Gate E e2e) proves in a real browser that the page CSP is enforced and the chem worker still starts. If a host ever applies a header CSP to workers, the chem worker script alone gets a policy that allows it; never the page.
- **Why**: a meta-tag policy does not apply to a dedicated worker, so the page can keep the strict policy while the worker runs RDKit; widening the page for one library would open every script on it. **Consequence**: the build smoke owns the "nowhere else" guarantee. **Rejected**: `'unsafe-eval'` on the page; replacing RDKit.

### ADR-036 — The navigator overview is built per ordered node pair; bundles know their total; hub expansion shows members
- **Decision** (reviewer, step 5.4c, 2026-10-07; refines GRAPH_SEMANTICS §3, §10, §11, supersedes nothing): (1) `navigatorProjection` builds the overview per ordered node PAIR: `limits.maxEdges` bounds drawn paths (pairs), pairs are admitted by (total descending, from, to), and the arrows drawn inside a pair are chosen by rank (selectivity, then IDs) in two passes (best edge per pair, then the spare budget to the smallest pairs first, up to `DEFAULT_DEGREE_CAP` each). (2) `EdgeBundle` gains a required `total`; `Truncation` gains the optional `hiddenPairs` and `hiddenEdges`; `GraphNode` gains the optional `hiddenMembers` (overflow nodes). (3) Hub expansion (`request.expansion.expanded`) shows members, with a member cap and one overflow node per hub (ADR-028), and counts nodes and structural edges against the limits. (4) `ProjectionDefinition.readsKinds` (additive; the navigator declares it, the other views declare nothing) and a pure `sameProjection`. (5) The roll-up index keeps a per-pair table and its candidates carry their substrate and product refs.
- **Why**: at 1,000 reactions the old overview was cut at 800 raw edges, a bundle did not know its real size (63 shown for a pair of 752), which pairs survived depended on IDs, and every arrow of a hub onto itself was one self-loop bundle (step 5.0 fact sheet). Counting pairs makes the limit match what is drawn, the full totals make the cut honest, and the data (size, then selectivity) decides what survives. `readsKinds` lets the projection hook skip rebuilds that cannot change the view (decision Q3).
- **Consequence**: no schema change, no `CURRENT_SCHEMA_VERSION` bump. Existing tests that encoded the cut at `maxEdges` changed (PROGRESS.md step 5.4c lists them). Exam scope and name are NOT ranking keys in the overview build; the full sorted list of a pair is read from the roll-up on demand (step 5.5b). `request.focus` and `collapsedEdgeIds` stay ignored (Phase 7).

### ADR-037 — Navigator as overview, family page and detail
- **Decision** (reviewer and user, step 5.5a review, 2026-10-09; refines ADR-036 and UI_ARCHITECTURE §3, §5, supersedes nothing): the navigator has THREE levels of detail. (1) The **overview map**: families (hubs) and plain arrows with their count; no arrow text, no hub expansion; its curated arrangement and family colours are step 5.5c. (2) The **family page** (step 5.5b): one family as a readable page, what it is made from and what it turns into, one card per reaction with structures, reagents and conditions. (3) The **reaction detail**: the inspector of steps 5.6a and 5.6b (mechanism, selectivity, stereochemistry, caveats, related reactions), opened from a card.
- **Principles.** Progressive disclosure: never everything at once. The chemistry, the IDs and the relationships are not simplified to make a picture cleaner: nothing is hidden, counts and links say where the rest is. Colour is for navigation and recognition, never decoration and never the only carrier of meaning. Quality comes from spacing, readable structures, short traceable arrows and a consistent interface. Visual direction (user): textbook calm with soft family colours (hydrocarbons blue, oxygen compounds green, halogen compounds amber, nitrogen compounds violet) and rounded cards (8 px cards and panels, 6 px controls).
- **2026-10-09 (step 5.5c, arrangement and colours as data; supersedes only the "no schema change" of the consequence below, for the arrangement)**: the curated arrangement of the overview is presentation DATA on the anchor, `navigator_anchor.cell` / `group` / `tone` (optional; schema version 2, migration 1 to 2 changes only the version; PRS-004 and PRS-005 warn). The overview is laid out on a grid by a pure layout in the layout worker when every anchored hub has a cell, and by ELK otherwise; the colours are tokens (a tint, a border and an ink per tone, WCAG 2.2 AA tested); the group is always written (accessible name, title, legend, family header), so colour is never the only carrier. Nothing about the arrangement is chemistry, and nothing is derived into storage.
- **Why**: one map of every family and every arrow is not studyable, and organic chemistry is cyclic, so a layered map loops back over itself. **Consequence**: no schema change. The family page is derived from the navigator roll-up index (a pure function in core), never stored. Hub expansion leaves the navigator; the projection's expansion and the expansion store stay for later views.
- **2026-10-11 (step 5.8, exam scope; refines the principles above, supersedes nothing)**: the exam scope is chosen in the top bar ("All (no exam scope)" or an exam version) and saved in `uiState`; it DIMS and MARKS IN WORDS, it never filters: the default request is unfiltered. A family is outside when it has reactions and all of them are (GRAPH_SEMANTICS dated line); on the family page and in the Unanchored panel each outside reaction is marked "outside <exam>". The default choice is All, not the latest version (JEE_ONTOLOGY §3 says "the latest official, else the latest provisional"; the reviewer's test plan chooses JEE Main to see Beckmann dimmed, so All is the start). No schema change.

### ADR-040 — Editor sessions
- **Decision** (reviewer, step 6.1a, 2026-10-17; refines ARCHITECTURE §23 and UI_ARCHITECTURE §7, supersedes nothing): (1) **Pure core module `src/core/editing`** (imports only core, zod, immer; clock and IDs through `CommandContext`): `openSession` (an `eds_` ID; `baseRecord` and `draft` are copies of the record; a new record starts as `{ kind, id }`), `editDraft` (Immer `produceWithPatches`; the inverse patches go on `past`, `future` is cleared, `updatedAt` set), `undoDraft` / `redoDraft` (exact: undo then redo returns the same draft), `compareForConflict`, `commitDraft`. (2) **Coalescing:** an edit to the SAME field path (the caller's `meta.path`) within 1,000 ms (injected clock) of the previous edit joins the previous undo step, so typing a word is one step. What coalescing needs (path and time of the latest edit) is kept in memory only, in a WeakMap keyed by the session value, never in the stored session: after a reload the next edit starts a new step. (3) **Bounds:** local history is at most 200 steps, oldest dropped first. (4) **Conflict:** the current record is compared with `baseRecord` by canonical text (`canonicalJson`, moved to `core/text` so core can use it; `io` re-exports it). The store's revision moving is NOT a conflict; a changed or deleted target is. `compareForConflict(base, current, draft)` gives per field path (top-level fields and one level into plain objects, e.g. `names.canonical`; arrays whole) base, theirs, mine and a status `same | theirsOnly | mineOnly | both` (both sides changed to the same value is `same`). (5) **Commit:** strict L1 parse first (findings with field paths, `reason: 'invalid'`), then the conflict check (`reason: 'conflict'` unless `choices` resolve every `both` field; `theirsOnly` fields take theirs, `mineOnly` take mine; the UI shows all of them; the merged record is parsed again), then ONE `store.dispatch` labelled "Edit <section> of <name>" with `expectedRevision` the store's revision at that moment. A `VALIDATION_FAILED` answer is `invalid` with its findings; any other refusal (read-only tab, ...) is the additive `reason: 'refused'` with the store's error. One commit is one global history entry. Provenance times: as the existing update builders, none set. (6) **Drafts kept (step 6.1a part 3):** every stored editor session is offered at boot (Save and Discard delete the row, so a row left at boot is an unfinished draft); the app's session manager (writer tab only) saves a dirty session at most every 2 s (a throttle) and on `visibilitychange` to hidden; at most 20 stored sessions; a row over 1 MB of JSON is not saved and the editor says so; one session per record; stored rows are untrusted (tolerant parse; an unreadable row is listed with Discard and never deleted without the user).
- **Why**: a draft may be invalid and long-lived, so it needs its own history and its own storage; the canonical store must change only through one validated command. **Consequence**: no schema or DB_STORES change; `DraftCommitOutcome` gains `refused` (additive); `BootReport.editorSessionIds` lists every stored session (PERSISTENCE §4 step 6 and §12, Amendments). **Rejected**: an unload-time write (not reliable, openItem 133); a debounce for saving (steady typing would never save); coalescing state in the stored session (it would survive a reload and merge steps across it).

D2 sections: Names, Identity, Structure, Formula and charge, Stereo, Aromaticity claim, Classes (with suggestions), Review (lifecycle editable, status read-only until 6.8); properties, notes and citations are read-only ("Editing arrives in step 6.6") and kept unchanged. D3 a new species starts as speciesKind `unspecified`, empty arrays, origin `user`, lifecycle `draft`, status `unreviewed`, times and ID from `CommandContext`; it needs a canonical name before it can save. D4 duplicate check on Save: "Open the existing", "Keep both", "Merge" unavailable ("Merging arrives in step 6.8").
